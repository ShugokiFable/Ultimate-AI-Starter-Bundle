# V7.4.2 CHANGELOG — MCP does work in Grok; I was reading a constant

> **PARTLY SUPERSEDED by v7.4.3.** The "keep Grok at five MCP servers"
> figure is wrong - five was never tested against six. The real cliff is 8
> RUNNING servers, and plugin-provided servers (e.g. `mcp-search` from
> claude-mem) count toward it without appearing in `config.toml`. Budget 6
> configured. Everything else in this release stands. See
> `V7.4.3-CHANGELOG.md`.


2026-08-16

v7.4.0 claimed Grok 1.0.4 "never attaches MCP tools" and shipped a config that
turned MCP off. **That claim was wrong**, and v7.4.1 built tooling on top of it.
Both are corrected here.

## What was wrong

The claim rested entirely on `tool_count: 26` being identical in every logged
turn — with 8 MCP servers and with 0. That looked like proof that no MCP tool
ever reached the model. It was not proof of anything. From Grok's own README:

| `search_tool` | Discover available integration tools (MCP) |
| `use_tool` | Call an integration tool discovered via `search_tool` |

**Grok deliberately never injects MCP tools into the tool list.** It ships those
two built-ins and discovers MCP tools on demand, to save context. `tool_count`
is the built-in count and stays 26 forever. I measured a constant and treated it
as a signal, without ever asking Grok to call a tool.

Asking it to call one settles it:

```
housecarl__housecarl_load_order_status  -> 2994 active plugins, profile Default
codebase-memory-mcp__list_projects      -> 45 projects indexed
```

Real data, two different servers. MCP works.

## What is actually true

The stall was real, and it is a **server-count limit**:

| Servers | `mcp_wait_ms` | Turn | Result |
|---|---|---|---|
| 1 | 0 | 2.5s | fine |
| 3 (local exes) | 0 | 5.2s | fine |
| 5 (3 local + github + context7) | 0 | 7.6–7.9s | fine |
| 7 | ~34 900 | — | never exits |
| 8 | ~34 900 | — | never exits |

Six or more wedges startup. It is not one bad server — dropping headroom from
the 8 did not help, and all nine probe healthy cold outside Grok (183 tools,
none slower than 1.4s).

**Guidance: keep Grok at five MCP servers or fewer.** The Claude-compat import
(`[compat.claude] mcps = true`) is what quietly pushes you over, because it
drags in every Claude Code plugin's MCP server as well.

Cause 1 is unaffected: inherited Claude hooks still cost a measured 60.037s per
turn, `hooks = false` still stands, and the `TOOLS/hooks/` stdin fix is still
correct and still needed.

## Changes

- `GROK-MCP-TROUBLESHOOTING.md` rewritten around the server-count limit, with
  the `tool_count` mistake documented rather than deleted.
- **Grok MCP wiring restored as an installer default.** v7.4.1 moved it behind
  `-WireGrokMcp` on a false premise. It wires four servers (housecarl,
  codebase-memory, headroom, Forge) — inside the safe range. `-SkipGrokMcp`
  opts out.
- The installer now **counts** the servers it leaves in `~/.grok/config.toml`
  and warns if the total reaches six.
- `[compat.claude] mcps = false` is still written, and now for the right reason:
  it keeps the Claude-plugin MCP import from silently pushing the count over the
  limit, while natively-declared servers keep working.
- v7.4.0 and v7.4.1 changelogs carry correction banners.

## The pattern worth naming

Three wrong calls across 7.3.0, 7.3.1 and 7.4.0, all the same shape: a plausible
story (orphan fleets), a misattributed observation (config rewrites), and a
constant mistaken for a signal (`tool_count`). Every one of them would have died
in seconds against a direct test — kill the theory by exercising the actual
behaviour, not by reading something adjacent to it. That is now the first line
of the troubleshooting cheat-sheet.
