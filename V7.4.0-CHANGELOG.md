# V7.4.0 CHANGELOG — the Grok softlock, actually measured

2026-08-16

v7.3.0 and v7.3.1 documented the Grok investigation while it was still open.
This release closes it, and corrects the parts that were wrong.

## What was actually wrong

A `grok -p "Reply with the single word: OK"` turn took **97 seconds**, of which
the model used **2.0 seconds**. Two independent causes, each isolated by A/B:

**1. Grok runs Claude Code's hooks.** Grok's Claude compatibility loads
`~/.claude/settings.json` plus every enabled plugin's `hooks/hooks.json` — 14
entries from 6 sources here. The two `Stop` hooks at `timeout: 30` cost a
measured **60.037s** per turn. Grok's docs state hook layers combine additively
and can never remove another layer's block, so `[compat.claude] hooks = false`
is the only lever. Post-inference stall after the change: **22ms**.

**2. Grok 1.0.4 never attaches MCP tools.** `tool_count` was **26 in all 12
turns ever recorded** — interactive and headless, 8 servers and 0 servers,
`~/.claude.json` and native `[mcp_servers]`. 26 is the built-in count; it is
identical with MCP entirely disabled. Meanwhile `mcp_wait_ms: ~34900` plus two
wake-gate timeouts charged **65s** to the first turn of every session. All 9
servers probe healthy outside Grok (183 tools, none slower than 1.4s), and the
stall scales with server *count*, not with any one server.

Turn time after both changes: **2.1–4.9s**, clean exit, every time.

## Corrections

- **Rule 1 ("never add `[mcp_servers]` to `config.toml`") was wrong.** Native
  sections were added, survived repeated runs, and `grok inspect` sourced them as
  `configToml`. The original "sections disappeared" observation was real but
  misattributed — most likely the `grok update --force-reinstall` run in the same
  window.

- **Rule 6 (orphan fleets) was wrong, and its tool was harmful.**
  `TOOLS/Clean-Grok-MCP-Orphans.ps1` is **removed**. The "orphaned Grok MCP
  fleet" it was written for was Claude Code's own running servers — the processes
  were children of `claude.exe` and no Grok process was alive. The script matched
  on process name only, with no parent check, so it killed every houseCARL,
  codebase-memory, headroom, Forge and npx MCP server on the machine, including
  ones other applications were actively using. Delete any copy you made.

- Rules 2–5 (pin npx, headroom launcher, cbm daemon, don't kill servers live)
  are kept and demoted to hygiene. All true; none of them was the softlock.

## Fixed: the hook gates could hang any host

`TOOLS/hooks/{completeness,assumption}_gate.py` called `sys.stdin.read()`, which
waits for EOF. A host that spawns the hook but never closes stdin — Grok does not
— left it blocked until the host's own timeout fired. Both files declare "fail
open: a broken gate must never be able to stop work" as design rule 3, and a
blocking read breaks that rule.

Three passes, because the first two looked fixed and were not:

1. Daemon thread + timed join — still hung; a daemon thread parked in
   `sys.stdin`'s `BufferedReader` holds its lock and blocks interpreter shutdown.
2. `os.read()` on the raw fd + `os._exit()` — `--pre` returned at 2.1s, `--stop`
   still hung.
3. A minimal repro found the real interaction: a thread parked on fd 0 plus a
   child inheriting stdin deadlocks on Windows (161ms with no reader, >12s with
   one, 2158ms with `stdin=DEVNULL`). `--pre` returns before touching git;
   `--stop` shells out to it, which is why only `--stop` hung.

Now: **2.2s** worst case with stdin open, **141–230ms** unchanged for
well-behaved hosts, both self-tests PASS, block decision still fires. Applied to
all four copies in the bundle.

## Housekeeping

- `GROK-MCP-TROUBLESHOOTING.md` rewritten around the measurements, with the
  corrections kept in place rather than quietly edited out.
- Verified all four installed provider skill trees are current against canonical
  (0 new, 0 updated). Grok needs no `~/.grok/skills`: it already loads all 92
  canonical skills through Claude compat, and a second copy would only add
  collisions to the 51 it already reports between bundle skills and plugin skills.
- 307.6 MB of stale backups removed from the live installs.

## Still open

- **51 skill collisions.** The canonical tree ships its own copies of skills the
  superpowers, obsidian and ponytail plugins also provide (`brainstorming`,
  `defuddle`, `json-canvas`, …). Grok reports each as `collidesWith`. The bundle
  is deliberately standalone, so this is a design question — dedupe against
  installed plugins, or keep shipping both — not a bug to silently fix.
- **MCP in Grok stays off** until a build ships where `tool_count` exceeds 26.
  The server definitions are commented in `~/.grok/config.toml`, so re-enabling
  is one edit and one `grok -p` to re-measure.
- Interactive `/mcps` behaviour after the fix is unverified here; the headless
  path and the turn log are what these numbers come from.
