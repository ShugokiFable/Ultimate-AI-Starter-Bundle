# V7.3.0 CHANGELOG — Grok hang forensics: documented so it never happens again

2026-08-15

## The incident

Grok sessions appeared to hang ("no reply") for an evening. Full forensics showed
the model, auth, proxy, and CLI were healthy the whole time — every stall was MCP
tool enumeration or a wedged pipeline:

- **35s tool-prep stall** (`shell.turn.tool_prep_done mcp_wait_ms: 34932`) while the
  model itself answered in 2.1s. Cancelling at ~30s kills the turn one second before
  the reply streams.
- headroom.exe crashed instantly under the Hermes-desktop-exported PYTHONPATH
  (3.11 venv packages loaded by a 3.12 binary) — same trap class as the Forge venv.
- codebase-memory daemon died with its console; the next spawn cold-booted it
  (`version_cohort.claimed_unheld`, ~30s first-turn stall).
- Unpinned npx servers (firecrawl, github) re-resolved the registry and could die
  past the 30s startup timeout.
- Grok's config manager **rewrote ~/.grok/config.toml and dropped user-added
  [mcp_servers] sections** — grok MCP config must live in the compat source only.
- Force-killing a server process under a live session wedged the pipeline.

## Pack changes

- **New: `GROK-MCP-TROUBLESHOOTING.md`** — symptom-first field guide: reading
  `unified.jsonl` turn phases, the five rules (no grok config.toml MCP sections,
  pin every npx server, headroom via launcher, cbm daemon keep-alive, never kill
  servers under a live session), and a diagnosis cheat-sheet.
- `TOOLS/MCP-CONFIG-EXAMPLES.toml.txt`: github pin example + "PIN EVERY npx
  server" rule with field-verified pins + pointer to the troubleshooting doc.
- `codebase-memory` skill: cold-daemon stall note (port check first, keep-alive
  host at login).
- Local installs: firecrawl @3.24.0 + github @2025.4.8 pinned in all provider
  MCP configs; headroom wired through the launcher for Grok/Claude/Codex/Kimi;
  grok config restored to zero MCP sections.
