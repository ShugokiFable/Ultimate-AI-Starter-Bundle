# v7.9.5 — Capability profiles

An external capability review proposed adding a set of MCP servers. Seven of
them are here. None of them is registered globally, and the reason is the
release.

**144 canonical skills** across five provider trees.

## What a connected server actually costs

`TOOLS\Test-McpHandshake.ps1` is new. It reads a provider's own config, spawns
each server exactly as that provider would, and runs the real MCP exchange —
`initialize` → `notifications/initialized` → `tools/list`. Against the live
configs on the development machine:

```
Claude   housecarl 45  skyrim-forge 52  github 45  firecrawl 25
         codebase-memory 15  headroom 3  context7 2  sequential-thinking 1
                                             188 tool schemas, every turn
Codex                                        136 tool schemas, every turn
Grok                                          90 tool schemas, every turn
```

A skill costs nothing until its description matches — 143 skill bodies are
~153,000 tokens against a ~5,500-token index. **MCP tool schemas have no such
discount.** Every tool of every connected server is in context on every turn of
every session, related or not.

So adding seven more servers globally would have been a straightforward
regression, in a release that arrives immediately after v7.9.2 argued the
opposite case.

## The profile router

`BUNDLED-TOOLS/PROFILES.json` declares named sets. `TOOLS\Set-McpProfile.ps1`
applies one only when **both** conditions hold: the project shows the profile's
markers, and the machine satisfies its requirements.

```powershell
TOOLS\Set-McpProfile.ps1 -List                    # what exists, what is ready
TOOLS\Set-McpProfile.ps1 -Detect -Path <project>  # what this project implies
TOOLS\Set-McpProfile.ps1 -Auto   -Path <project>  # detect and wire
TOOLS\Set-McpProfile.ps1 -Disable web             # give the context back
```

| profile | servers | gate |
|---|---|---|
| `code-deep` | Serena 1.7.0 | uv — **auto-installed** |
| `web` | Chrome DevTools 1.7.0, shadcn 4.18.0 | Google Chrome; `components.json` |
| `cloud` | Supabase 0.11.0 | `SUPABASE_ACCESS_TOKEN` |
| `engine-blender` | blender-mcp 1.8.3 | Blender installed |
| `engine-godot` | godot-mcp 0.1.1 | `GODOT_PATH` |
| `engine-unity` | Unity-MCP 0.89.0 | the package installed in that project |

A profile it cannot run is skipped **with the reason printed** — never written
as a config entry that fails on first call. That failure is invisible from the
outside: a provider that cannot spawn a server shows no tools and says nothing
about why.

The installer runs `-Auto` against `-WorkspaceRoot` when one is given, so a
normal install wires what the workspace implies and nothing else.

### Details that are not incidental

- **Serena is registered with a per-client `--context`.** It ships named
  contexts for `claude-code`, `codex` and `grok` that trim its tool set to what
  the client does not already provide; Kimi and Hermes have none and get the
  generic `agent` context. `--enable-web-dashboard false` stops a browser window
  opening on every session start.
- **Supabase carries `--read-only`.** An agent that can `DROP` a production
  table on a misread is not a capability, it is an incident.
- **Chrome DevTools carries `--no-usage-statistics`.** Upstream telemetry is on
  by default; this pack does not enable third-party telemetry on someone's
  machine without asking.
- **Unity is project-scoped by construction.** There is no machine-wide server:
  the executable is generated inside the project's `Library` folder by the Unity
  package. Until that package is installed the path does not exist, and the
  profile refuses rather than writing it.
- **Blender's editor half is stated, not faked.** `uvx blender-mcp install-addon`
  places the addon, but enabling it happens inside Blender. The profile prints
  the step instead of claiming it ran it.

### Evaluated and not shipped

- **Unreal MCP** (`runreal/unreal-mcp`) — last upstream commit 2025-06-06, 113
  stars. A bridge into a running editor is exactly what breaks on an engine
  point release. Vendoring an unmaintained one under a version number that
  implies exact-version discipline would be a false claim.
- **Storybook** — no first-party server. Community servers exist; none had
  provenance this pack would accept for an unattended install on a user's
  machine.

Both are listed in `PROFILES.json` under `evaluated_not_shipped`, with the
reason, and `-List` prints them. A capability declined on purpose is a decision;
one declined silently is a gap nobody knows about.

## One writer for three config shapes

Four providers store MCP servers three ways: two JSON files with different
section names, two TOML files, and Hermes through its own Python config API.
Every config bug this pack has shipped was a bug in one shape that the other two
did not have — a TOML matcher that stopped at the `[` inside
`args = ["-y", ...]`, a Hermes check that read `mcp list` output (names, never
commands) for a package string, a backslash escaped four times instead of two.

`TOOLS/V7-Mcp-Write.ps1` is now the only place this pack writes an MCP entry.
Both `Add-Reasoning-MCPs.ps1` and `Set-McpProfile.ps1` use it.

`TESTS/Test-McpProfiles.ps1` covers it, entirely against temp files, and caught
two defects on its first run:

- **PowerShell unrolls a single-element array on `return`.** `blender-mcp` takes
  exactly one argument, so it would have been written as `"args": "blender-mcp"`
  — a string where the provider expects a list.
- **`-CheckOnly` deleted the entries it claimed it would only report on.** The
  retirement pass ran before the add pass and had no dry-run of its own. A dry
  run that writes is worse than no dry run, because it is trusted.

## A live defect only the handshake could find

With the gate green, the probe was pointed at the real configs. Codex failed:

```
playwright-mcp    FAIL no initialize response within 75s
```

The entry read `args = ["@playwright/mcp@latest", "--executable-path", ...]` —
unpinned, and missing `-y`, so `npx` blocked forever on an install prompt.
v7.9.2 pinned Playwright to `0.0.79` in the catalog. The pin never arrived,
because `Update-V5GrokMcpBlock -SkipIfPresent` compared only the **command** —
and every npx server has the same command, `npx`, so the comparison always
matched and the args were never looked at.

Same shape as the withdrawn GitHub package one release earlier: **a fix that
cannot reach the machines that need it is not a fix.** `-SkipIfPresent` now
compares the args too, rewrites once when they have drifted, and no-ops
afterwards. The values there are derived entirely from the catalog and one
environment variable, so there is no hand-authored setting to protect.

The probe itself had a matching blind spot: it could not read TOML *literal*
strings (`command = 'C:\path\to.exe'`), which is the form Codex writes for its
own entries, so two real servers were missing from the first report. A
diagnostic that under-reports is worse than none.

## Five more, found by running it

The gate was green and CI was green. Then the probe was pointed at live configs,
and everything below came out of that — none of it visible to a static check.

**Playwright was pinned but still hung.** Repairing the drifted entry printed the
catalog's own arguments: `["@playwright/mcp@0.0.79"]`, with no `-y`. The pin was
never the whole bug. Without `-y`, `npx` prompts before installing a package that
is not cached, and a prompt on a redirected stdin never returns. Every other npx
entry in the catalog had `-y`; this one did not.

**So the contract sweeps instead of enumerating.** The first version of the new
test checked `-y` and a version pin for the servers in `PROFILES.json` — the ones
being added. It would have passed while `CATALOG.json` shipped the broken entry.
Widened to every npx component in either file, it immediately found two more:
`firecrawl-mcp` and `@perplexity-ai/mcp-server` were unpinned, in the catalog
whose own scope notes explain why unpinned npx is dangerous. Pinned to `3.24.0`
and `1.2.0`, both verified against the npm registry.

**The probe deadlocked on its own diagnostic.** Serena reported
`no initialize response within 120s` while running perfectly by hand. The probe
redirected stderr and never read it; a redirected pipe nobody drains fills at
about 4KB and blocks the writer, and Serena logs ~20 startup lines before it
serves anything. A false FAIL is the worst possible output from a tool whose job
is telling a real failure from a configuration mistake. stderr is now drained
asynchronously, and a genuine failure quotes its tail.

**Grok would have registered a profile twice.** Grok reads `~/.claude.json` as
well as its own config, so a profile enabled for both providers produced two
entries under one name — two handshakes for one server, against a CLI that
wedges at eight. The core wiring already skipped what Grok inherits; the profile
router did not. Fixed, and the inherited list is read *inside* the provider loop:
Claude is written earlier in the same pass, so a snapshot taken up front would
never see what had just been added.

**Three dead command paths on Codex, and the repair tool could not fix them.**
`Repair-McpPaths.ps1` found all three and reported `no replacement found`. Its
rule is "a version-stamped sibling (`Name-1.2.3`)" — this pack's own convention.
Codex keys its runtime directories by content hash:

```
...\runtimes\cua_node\2fb562745e6d66f0\bin\node_repl.exe   dead
...\runtimes\cua_node\84464046935436b8\bin\node_repl.exe   installed
```

Same failure, same silence, a name that is not a version. The rule is now
generalised to **exactly one sibling directory under which the remaining tail
exists** — uniqueness is what makes it a resolution rather than a guess, and two
candidates stay reported for a human to choose. All three repaired; `node_repl`
answers again.

## Known limits

- The profiles are **Windows-first**, matching this pack's installer target.
  Detection paths for Chrome and Blender name Windows install locations.
- **Editor bridges need the editor.** Blender, Godot and Unity servers register
  successfully and answer nothing until the companion plugin is running. The
  profile says so; it cannot fix it.
- `-Auto` detection is **top level only**. A recursive scan of a large tree
  would be slow and would match a marker inside a vendored dependency.
- Serena's install is ~250 MB of Python dependencies via `uv`. It runs only when
  `code-deep` is enabled, never during a plain install.
