# v8.7.0 -- the desktop, and a router that makes 41,768 tokens into 2,846

**2026-08-27.** Based on v8.6.13. **164 canonical skills**, unchanged. Two new
catalog components, one new profile, and two defects found by measuring them.

Fifteen projects were recommended into this pack from outside. Every one of them
exists and does roughly what was claimed, and the recommendation carried no
maturity data at all -- which is the only axis that decides whether a bundle
vendors something. Checked against the GitHub API, two survived. What follows is
what measuring them produced.

---

## The desktop was the one surface this pack could not reach

Playwright and chrome-devtools stop at the browser. `windows-mcp` drives the
machine: click, type, shortcuts, PowerShell, registry, filesystem, windows and
processes, through UI Automation -- which also lets an agent read controls
without spending a vision call on a screenshot.

Measured with `TOOLS\Measure-McpSchemaCost.ps1` against
`uvx windows-mcp@0.8.5 serve`:

| | tools | schema bytes | tokens/turn |
|---|---|---|---|
| **windows-mcp** | 20 | 22,088 | **~5,522** |
| firecrawl-mcp (not registered) | 25 | 36,337 | ~9,084 |
| context7 (always-on) | 2 | 5,124 | ~1,281 |

Cheap for an entire operating surface. Shipped as the `windows` profile, **off
by default**, `scope: global` (a desktop is not a property of a repository), and
carrying **no detect markers at all** -- `-Auto` can never reach it. `reasoning`
has an empty detect block because a way of thinking is not a property of a
directory; this one is empty because no file on disk is evidence that an
operator wants an agent clicking their mouse.

    TOOLS\Set-McpProfile.ps1 -Enable windows -Global

## The capability sweep would have driven that desktop

`TOOLS/measure_mcp_capability.py` calls **every** tool a server advertises, with
arguments synthesized from each schema. Correct against a web API. windows-mcp
advertises `Click`, `Type`, `Shortcut`, `PowerShell`, `Registry`, `Clipboard`,
`MultiEdit`, `Process`, `App` and `FileSystem`.

Its only protection was `MUTATING_HINTS`, a blocklist of name fragments:
*create, update, delete, remove, write, push, merge, close, add, set, post,
send, upload, fork, rename, move, start, stop, cancel, run, execute, install,
publish, revoke.* Every one of those is a verb a REST API would use. Not one
matches `Click` or `Registry`.

This was measured, not reasoned about. The sweep ran and really did call
`FileSystem`, `Snapshot`, `Scrape`, `DisplayInventory` and `Wait`. `FileSystem`
takes `mode` as an enum and the argument synthesizer picks `enum[0]`. Upstream
happens to list it as `["read", "write", "copy", "move", "delete", "list"]`, so
the call was a read of a nonexistent path. **Had the enum been ordered
`["write", ...]` the sweep would have written a file.** The safety of that call
rested on the ordering of somebody else's enum.

The blocklist is extended, but extending it is the floor, not the fix -- `App`
and `FileSystem` still match nothing, and this file already knows what is wrong
with blocklists, because its environment handling was converted to an allowlist
for the same reason. So a server that drives the machine is **not swept at
all**. Which servers those are is a CATALOG fact (`controls_machine`), not a
guess about spelling, the refusal fires before any tool is called, and it names
the read-only tool that answers the same question.

## A proxy MCP turns 41,768 tokens per turn into 2,846

houseCARL wired directly is 45 tools, 167,072 bytes, **41,768 tokens on every
turn**, and Claude, Codex, Grok and Kimi cannot filter individual tools the way
Hermes can -- on those four it is all 45 or nothing. That is why
`game-skyrim-load-order` has been off.

`super-mcp-router` registers **one** server with 11 meta-tools and puts
everything else behind on-demand discovery. Measured: **11 tools, 11,386 bytes,
~2,846 tokens per turn** -- and that number does not grow as more servers go
behind it.

Proven end to end against this pack's own houseCARL, not asserted:

```
search_tools("list the plugins in the active load order")   5 hits,  400ms
get_tool_details([housecarl__housecarl_load_order_status])  3,652 chars
                                                            ~913 tokens, 200ms
use_tool(...)  ->  2,999 mods, 2,995 plugins, live from the shim
```

So: 2,846 per turn, plus ~900 once per novel tool, against 41,768 every turn.

**It is not wired into a profile, and the reason is specific rather than
cautious.** The router reads its own config at
`%USERPROFILE%\.super-mcp\config.json`, so enabling it means this pack writing
and preserving a *third-party tool's* config file -- a second config writer with
its own merge obligations, on a 24-star dependency. The measurement is what
ships here; the wiring is its own release.

One caveat recorded for that decision: BM25 ranking returned
`housecarl_merge_plugins` **first** for that read-only query, with the correct
`housecarl_load_order_status` third. Discovery works. The top hit is not
automatically the safe one.

## The measurement tool had been sending a byte order mark

Windows PowerShell 5.1 puts `EF BB BF` in front of the first frame written to a
child's stdin. windows-mcp's pydantic parser rejects the whole initialize
message for it:

```
Invalid JSON: expected value at line 1 column 1
[type=json_invalid, input_value='\ufeff{"method":"initialize"...
```

Every server measured before it had tolerated the BOM in silence, which is how a
tool whose entire job is speaking MCP the way a provider does spent seven
releases sending something no provider sends.

The fix is specific, and the specificity is the point. Wrapping
`StandardInput.BaseStream` in a BOM-less `StreamWriter` does **not** work --
reading `.StandardInput` builds .NET's own writer and sets `AutoFlush`, and
`Flush()` emits the preamble before this script ever has a handle. That was
tried first and the child still received `EF BB BF`. `Console::InputEncoding` is
what that writer is constructed from, so it is the only lever early enough, and
it has to be set before `Process.Start`. Restored afterwards, so measuring a
server does not change the encoding for whatever runs next.

## Contract

**109 contracts, green.** Three new, and every one of them was broken on purpose
before being trusted -- seven mutations, seven caught by the assertion under
test, with the tree restored byte-exact afterwards:

- `test_a_machine_controlling_server_is_never_swept_by_calling_its_tools`
- `test_desktop_control_can_never_be_switched_on_by_detection`
- `test_the_schema_cost_tool_does_not_send_a_byte_order_mark`

That exercise earned its keep twice. The BOM contract originally matched the
string `[Console]::InputEncoding`, which is also present on the line that only
*reads* the previous value -- so deleting the fix left the assertion green and
failed later with `substring not found` instead of saying what broke. It now
binds to the assignment.
