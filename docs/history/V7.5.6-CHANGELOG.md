# v7.5.6 CHANGELOG - PS 5.1 native-stderr fix + mojibake sweep

2026-08-18

## The user-visible bug

A live install on the operator's machine printed this during the Headroom
component step:

```text
python.exe :
At ...\INSTALL-V7-AIO.ps1:376 char:40
+ ... else { & $py -m pip install --user $asset 2>&1 | Out-H ...
    + CategoryInfo          : NotSpecified: (:String) [], RemoteException
    + FullyQualifiedErrorId : NativeCommandError
```

pip had written "Requirement already satisfied" and its version notice to
stderr. With `2>&1`, PowerShell 5.1 wraps every stderr line in an ErrorRecord.
The v7.5.1 fix had already set `$ErrorActionPreference='Continue'` around the
pip step, so the installer *survived* — but each record still printed as a red
`RemoteException / NativeCommandError` block that looks exactly like a crash.

## Root cause, and why it was worse elsewhere

- **pip step (cosmetic):** EAP=Continue + `Out-Host` — ErrorRecords reach the
  host and render as errors. Non-terminating, but indistinguishable from a
  failure for the user.
- **npm `-g`, `npx` plugin installs, `claude mcp add` (latent crash):** these
  ran under the script-wide `$ErrorActionPreference='Stop'` (line 96). Any
  stderr write from those tools is a *terminating* NativeCommandError —
  reproduced on PS 5.1: the old pattern terminates with NativeCommandError the
  moment the native command writes one byte to stderr. npm's try/catch turned
  it into a false "npm global failed"; the `claude mcp add` call had no
  try/catch at all and could abort the whole installer.

## The fix: Invoke-V5Native

One helper in `INSTALL-V7-AIO.ps1`, now used by all four call sites:

- drops EAP to `Continue` locally (restore in `finally`),
- stringifies every output line (`ForEach-Object { Write-Host ("  " + $_) }`)
  so ErrorRecords never reach the host's error formatting,
- returns success from `$LASTEXITCODE`.

Verified on PS 5.1 with a fake native command: stderr prints as plain text,
exit 0 -> `$true`, exit 3 -> `$false`, caller's EAP untouched.

## Bonus measured gotcha: never name a parameter `$Args`

The first version of the helper used `param([string]$Exe, [string[]]$Args)`.
Splatting worked, stderr was clean — and `$LASTEXITCODE` inside the function
was always `$null`, so every call reported success. Shadowing the automatic
`$Args` variable silently breaks exit-code propagation in PS 5.1 (measured;
parameter renamed to `$ArgList`). This would have turned every tool-install
failure into a silent "OK". The helper's comment now documents it.

## playwright-mcp no longer forces Google Chrome

With no flags, `playwright-mcp` defaults to the Google Chrome channel and
nags you to install Chrome — even if your daily driver is Opera GX, Brave,
Vivaldi, or Edge.

- `BUNDLED-TOOLS/CATALOG.json`: `playwright-mcp` gains
  `extra_args_env` = `PLAYWRIGHT_MCP_EXECUTABLE_PATH` +
  `extra_args_template` = `["--executable-path", "{value}"]`, and a
  browser-choice paragraph in its `scope_note` (with the Opera GX example).
- `INSTALL-V7-AIO.ps1` `mcp-npx` branch: when the named user env var is set,
  the template args are appended to the wired MCP args for every provider
  (Grok/Codex TOML, Claude `mcp add`, printed blocks). Unset: installs behave
  as before and the installer says so.
- Verified live on the operator's machine: Opera GX 134
  (`%LOCALAPPDATA%\Programs\Opera GX\opera.exe`) answers CDP
  (`/json/version` returns a `webSocketDebuggerUrl`, HeadlessChrome/150 with
  `OPR/134` in the UA) — exactly what playwright-mcp connects to.
  `PLAYWRIGHT_MCP_EXECUTABLE_PATH` is set for the operator and the live
  Kimi/Codex MCP entries were updated to it.

To switch browsers later: edit the `args` array in the provider's MCP config
(Grok/Codex `config.toml`, Kimi `~/.kimi-code/mcp.json`) or re-run the
installer with the env var pointed elsewhere.
