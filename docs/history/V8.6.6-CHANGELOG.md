# v8.6.6 -- the index was full of the pack's own skills

**2026-08-26.** Based on v8.6.5. **164 canonical skills**, up from 160. A local
audit that found the skills index spending a third of its budget on duplicates
of this pack, 1.29 GB of leftovers from a tool that was already uninstalled, and
a benchmark claim of our own that no longer reproduced.

---

## The index was two-thirds pack and one-third echo

Codex renders its skills index into a fixed budget and splits it across every
entry, so entry count decides how much description each skill gets to show. A
skill with no description cannot be chosen: the model has nothing to choose on.

Measured before and after:

| | before | after |
|---|---|---|
| index entries | 211 | **180** |
| from plugins | 71 | **40** |
| visible description chars | **32** | **52** |
| skills indexed twice | **18** | **0** |
| installed-state doctor | FAIL, 29 errors | **PASS** |
| `~/.claude/plugins` on disk | 1.4 GB | **128 MB** |

Descriptions are **63% wider on every skill**, and nothing was given up to get
there.

### `anthropic-skills` was serving this pack its own skills back, stale

The plugin contributing 26 entries was not an Anthropic skill set. Its manifest
says `"creatorType": "user"`: it was **this machine's own skills**, uploaded to
Cowork and served back as a plugin. Fourteen of the 26 were pack skills --
`skyrim-tool-router`, `unrestraint-packs`, `housecarl`, `fictional-adult-modding`
among them -- and they no longer matched canonical, because canonical had moved
on since the upload. So they were not merely duplicates, they were **stale
shadows of live skills**, competing for the same index budget.

Of the remaining twelve, five duplicate Codex's own `documents` / `pdf` /
`spreadsheets` / `presentations` / `template-creator` runtime plugins. The rest
are Cowork management. Usage count since 2026-07-13: **zero**.

The `obsidian` plugin went the same way: all five of its skills are already
carried here, byte-identical once line endings are normalised, and its usage
count was also zero.

Both are **disabled, not deleted** -- `enabled = false` in
`~/.codex/config.toml` and dropped from `enabledPlugins`, so either comes back
with one edit.

## 29 skills had drifted, on four providers

The doctor was failing before any of this, and had been. `ai-tooling-stack` was
stale on Codex, Grok, Kimi and Hermes simultaneously; Codex carried 24 modified
skills. A `-SkillsOnly -AllProviders` resync cleared all 29. Grok and Hermes now
account 160-of-160 exact where they were 159.

## 1.29 GB of a tool that was already gone

claude-mem was uninstalled in v8.6.4's cleanup. What survived it: two 271 MB
`temp_*` marketplace clones, a 478 MB plugin cache, a third 271 MB clone, an
install manifest, a dead marketplace entry in `settings.json`, and four
telemetry records. Removal is not removal until the cache goes too.

## Four skills adopted, eleven rejected

From `anthropics/claude-plugins-official`, Apache-2.0, redistributable with
attribution:

- **`skill-creator`** -- authoring, evaluating and benchmarking skills, with
  description-tuning for trigger accuracy. This pack's entire product is 164
  skills; it had no skill for writing one.
- **`build-mcp-server` + `build-mcpb` + `build-mcp-app`** -- taken as a set
  because the first explicitly hands off to the other two. MCP registration is
  core to this pack; authoring was not covered.

They go in `_CANONICAL-SKILLS/`, which installs to **all five providers**. That
is the whole reason to adopt rather than enable a plugin: a plugin serves one
provider, a canonical skill serves five. It is the same lever that made the
index worse when it pointed the other way.

Reviewed and **rejected**, recorded in
`_CANONICAL-SKILLS/THIRD-PARTY-NOTICES.md` so it is not re-litigated:
`hookify/writing-rules` (documents a tool this pack does not install),
`claude-security` (`disable-model-invocation`, drives Claude-only agent panels,
and `security-boundaries` / `secret-hygiene` / `supply-chain-verification`
already exist here), `claude-md-improver` (would rewrite the same `CLAUDE.md`
this pack's preamble wiring owns), and `plugin-dev/*` plus seven others as
Claude-specific or off-mission.

The pack's own identity contract caught the one thing that should not ship:
`build-mcp-server/references/auth.md` carried a real address. The guard was left
strict and the adopted file changed instead.

## RTK vs OMNI, and a claim of ours that had rotted

Both are `cli-optional` and neither is auto-installed. v8.6.5 catalogued them on
upstream numbers; they are now measured on this repository's git corpus.

| | rtk 0.45.0 | omni 0.7.8 |
|---|---|---|
| whole corpus | **85.2%** | 71.2% |
| lossless rows only | -- | **6.4%** |

**OMNI's 71.2% is mostly truncation.** Two commands exceeded a 65,536-byte cap
and its own marker says what happened: `full output not archived`. Above that
cap the bytes are gone, which the README's byte-for-byte guarantee does not
qualify. Excluding those rows, its real recoverable saving was 6.4% -- close to
its own honest published 8.8% on git, which suggests the tool's self-reported
numbers are sound and only the *apparent* large wins are truncation.

Below the cap the guarantee holds and verifies: a 33,453-byte diff came back
byte-identical, and the retrieve handle **is** the content's SHA-256 prefix, so
retrieval checks itself.

They are not competitors. OMNI's README says it better than our catalog did --
the ledger "removes bytes because they are already in the context, not because a
pattern calls them noise", which is "the half a filter cannot do."

**And the rtk entry was quoting a number that no longer existed.** It claimed
97% from `git diff HEAD~3`. `HEAD~3` moves with every commit: the raw output was
2,010,426 bytes when measured and is 308,076 now, and the saving measures 82.5%
today. It is pinned to tag ranges with the honest spread -- 25.3% on one release
delta, 87.4% across four. This catalog told OMNI to publish its 5% instead of its
97% best case; it was not holding itself to that.
