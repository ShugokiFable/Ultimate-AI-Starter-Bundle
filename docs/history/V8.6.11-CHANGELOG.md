# v8.6.11 -- rtk is a git tool, and `rtk find` is upstream-broken

**2026-08-27.** Based on v8.6.10. **164 canonical skills**, unchanged. Every rtk
number this pack had ever shipped was a git command; measured off git the same
tool aggregates 7.4%. A blanket claim the pack repeated in two documents turned
out to be false, `rtk find` breaks on compound predicates with ten-plus open
issues upstream, and two JSON files stopped carrying a byte-order mark.

---

## The BOM, finally

`BUNDLED-TOOLS/CATALOG.json` and `BUNDLED-TOOLS/OFFLINE-MANIFEST.json` each
began with `EF BB BF`. Every reader *inside* the pack opens `utf-8-sig`, so it
never surfaced here -- but it surfaced in what shipped:

`build_release.py` regenerates `OFFLINE-MANIFEST.json` for the Core archive
through `json.dumps(...).encode('utf-8')` and therefore shipped it **BOM-less**,
while the source tree and the Full archive shipped the same logical file with
three extra leading bytes. Same file, two encodings, decided by which archive
you downloaded. `json.load(open(path))` -- the obvious call, and the one any
consumer outside this repo writes -- fails on one and succeeds on the other.

These are also the same three bytes that broke `START-HERE.bat` in two separate
releases. Both files were stripped, with the parsed content compared before and
after to prove only the prefix changed. `VALIDATION.json`, named alongside them
in earlier notes, never had one.

The contract walks all **148** JSON files in `MANIFEST.json` rather than naming
the two known offenders, so a BOM entering through any new file fails too. It
reads MANIFEST and not `git ls-files` because this suite also runs from an
extracted archive, where there is no git. Falsified by re-adding a BOM to
`CATALOG.json` and, separately, to a file the contract never names.

## rtk, off the git corpus

Every figure this pack shipped for rtk -- 87%, 88%, 25%, 0%, and the retired
97% -- came from a `git` command. rtk's own pitch is loudest about build output,
test runners and logs, and those had never been measured. At **0.46.0**, same
repo, stdout only:

| Command | Native | rtk | Saved | Fidelity |
|---|---|---|---|---|
| `rtk err <powershell pack gate>` | 5,746 B | 567 B | **90.1%** | subset |
| `rtk test <python suite, RED>` | 5,507 B | ~400 B | **93%** | FAIL line kept |
| `rtk ls -la` | 811 B | 271 B | 66.6% | rewritten |
| `rtk ls -R` | 25,059 B | 19,129 B | 23.7% | rewritten |
| `rtk grep -rn` | 17,588 B | 14,463 B | 17.8% | **truncates** |
| `rtk wc -l` | 5,414 B | 5,003 B | 7.6% | rewritten |
| `rtk read` (191 KB) | 191,795 B | 191,795 B | **0.0%** | byte-identical |
| `rtk json` (5,425 rows) | 1,121,123 B | 144 B | *100%* | **truncates** |
| `rtk find` **compound** (`-not -path`) | 4,869 B | **0 B** | -- | **exit 1** |
| `rtk find` simple (`-name`) | 709 B | 565 B | 20.3% | paths stripped |

**Excluding rows that truncate rather than compress: 7.4%, against 85.2% on
git the same day.** rtk is a git tool that also ships filters.

### Three corrections the first pass forced

**stderr was contaminating every row.** rtk writes a 78-byte
`No hook installed` nag to stderr on *every* invocation. Captured combined with
stdout it inverts small results -- the `find` row measured **-486%** before
stderr was excluded. Anyone benchmarking this tool with `2>&1` is measuring the
nag, not the filter.

**`rtk read` is byte-identical, not a 0.1% loss.** The apparent +78 bytes was
the same nag. Redirected to a file it reproduces `cat` exactly -- which
confirms the catalog's existing claim, and also means it saves nothing.

**100% is not always a saving.** `rtk json` returns 144 bytes from 1.1 MB by
printing one array element and `... +5424 more`. That is a sample, the same
trap as lean-ctx's `-m map` last release: a different operation wearing a
compression ratio.

### `rtk find` breaks on compound predicates

The first pass measured `-name '*.ps1' -not -path './.git/*'` and concluded rtk
shell-expands the pattern. **That was wrong**, and it was caught before this
release was tagged. A simple `rtk find TOOLS -name '*.ps1'` works: 709 -> 565 B,
24 files, exit 0. The **compound predicate** is what fails -- `-not -path`
returns 0 bytes with exit 1 and `paths must precede expression` on stderr.

Upstream knows. `rtk-ai/rtk` has ten-plus open issues against `rtk find` alone,
including four near-duplicate reports of this exact limitation (#2469, #2847,
#3256, #3458), silent omission of gitignored (#3656) and hidden (#3291) files,
and **#3410**: the `find` rewrite rule is *unconditional*, so
`find ... -delete` / `-exec` is captured and refused -- silently doing nothing
and breaking `&&` chains. That one is their report, not measured here.

`rtk find` also reformats paths rather than listing them: single-directory mode
drops the prefix, multi-directory mode regroups under a `10F 2D:` header.

### Correction: rtk does not always discard

This pack shipped, in the README *and* the catalog, that rtk keeps **"no
archive and no retrieval"**. That was measured on `git` and generalised. Watched
per subcommand:

| Subcommand | Tee archive |
|---|---|
| `rtk test` | **complete** -- all 96 result lines, and it prints the path |
| `rtk grep` | partial -- 6,482 of 17,588 B, **and it prints the retrieval command** |
| `rtk git`, `ls`, `read`, `json`, `wc` | none |

The blanket claim was false for exactly the subcommand where an archive matters
most: a test runner, where you filter down to the failure and may then want the
full log back. `rtk grep` cuts each file at 25 hits and appends
`+28 more in <file> [see remaining: tail -n +26 "<tee path>"]`, so its
truncation is recoverable too.

Beyond bytes, the filters drop things worth naming, because `-g` applies them to
commands you never opted into: `rtk ls -la` removes **timestamps and owner** and
rounds sizes (`36.6K` for 37,481 B) -- the two usual reasons to pass `-la`;
`rtk grep` abbreviates middle path segments; `rtk find` strips or regroups
directory prefixes.

### The hook stays off, now on evidence

`rtk hook claude` was fed real payloads to see what `-g` actually automates:

| Typed | Rewritten to | Measured |
|---|---|---|
| `git status` | `rtk git status` | 85.2% -- the real win |
| `ls -la` | `rtk ls -la` | 24-67% |
| `grep -rn foo .` | `rtk grep ...` | 17.8%, truncates |
| `cat README.md` | `rtk read README.md` | **0.0%** -- pure overhead |
| `find . -name '*.ps1' -not ...` | `rtk find ...` | **breaks** (compound) |
| `npm test`, `curl`, `python x.py` | *not rewritten* | -- |

The hook automates the categories that measure worst or break outright,
and does **not** automate `rtk err` / `rtk test` on a test runner -- the only
strong non-git rows. Keep the binary, invoke those deliberately, leave the hook
off. That was already the default; it is now a measured decision rather than a
cautious one.

Full working in `docs/TOOL-EVALUATIONS.md`.
