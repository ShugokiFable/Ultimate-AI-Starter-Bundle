# v7.7.1 - the installer would have unwired Codex

v7.7.0 wired all five providers and verified the live machine. It also shipped
an installer that, on its next run, would have taken one of them back apart.

## The two halves Codex needs, and the one that got dropped

Codex resolves `superpowers@ultimate-bundle` through three files that have to
agree:

| file | says |
|---|---|
| `~/.codex/config.toml` | `[marketplaces.ultimate-bundle]` -> a source path |
| that source's `.claude-plugin/marketplace.json` | which plugins the marketplace offers |
| `~/.codex/config.toml` | `[plugins."superpowers@ultimate-bundle"] enabled = true` |

`INSTALL-V7-AIO.ps1` gets this right: its Codex branch stages the bundled
superpowers tree into the marketplace and calls
`Add-V5MarketplacePluginEntry` to declare it.

Then, later in the same run, `Install-Completeness-Gate.ps1` does this:

```powershell
if (Test-Path -LiteralPath $marketRoot) { Remove-Item -LiteralPath $marketRoot -Recurse -Force }
New-Item -ItemType Directory -Force -Path $marketRoot | Out-Null
Copy-Item -Path (Join-Path $pluginSrc '*') -Destination $marketRoot -Recurse -Force
```

The marketplace is deleted and rebuilt from `TOOLS/hooks/plugin/`, whose
manifest declares `completeness-gate` and nothing else. The superpowers entry
written minutes earlier is gone. The gate then stages the superpowers *tree*
beside it and leaves `config.toml` alone - `[plugins."superpowers@ultimate-
bundle"]` is already present, so it is not re-added.

Result: Codex enabling a plugin that its own marketplace does not list, with
the plugin's files sitting right there undeclared. Nothing errors. It just
does not load.

The gate now declares superpowers in the manifest it just rebuilt, gated on
the staged tree actually being present - the same rule it already applied to
the `config.toml` entry, which is why that half never broke.

### Proved, not assumed

Both versions of the gate were run against a throwaway
`USERPROFILE`/`LOCALAPPDATA` seeded with the real-world starting state (a
`config.toml` that already enables superpowers):

```text
[BEFORE - v7.7.0 as shipped]
  manifest declares : completeness-gate
  superpowers tree  : True
  config + manifest agree: False

[AFTER - patched]
  manifest declares : superpowers, completeness-gate
  superpowers tree  : True
  config + manifest agree: True
```

## Codex and Grok stop reporting SKIP

v7.7.0's harness test refused to give Codex and Grok a verdict, on the
grounds that a staged plugin directory is not proof a harness loaded it. That
reasoning was right about staged directories and wrong about these two
providers, because both keep a registry of their own:

- Grok: `~/.grok/installed-plugins/registry.json`, naming the repo, the
  plugins it provides, and the path it was installed to.
- Codex: `config.toml`'s marketplace + plugin tables, plus the marketplace
  manifest they point at.

That is the loader's own source of truth - the same class of evidence as
Kimi's `installed.json`, which v7.7.0 already accepted. Reading it is not
inventing a verdict.

`Test-HarnessRealization.ps1` now walks both chains end to end and checks that
every link resolves on disk. **18 pass, 0 fail, 0 skip** (was 16/0/2).

The Codex check earns its place: run against a marketplace manifest missing
the superpowers entry, it reports

```text
Codex     native superpowers   FAIL  config.toml enables it but the marketplace manifest does not declare it
```

which is precisely the state the old gate left behind.

## "Kimi has no hook or plugin system" was false twice over

`Install-Completeness-Gate.ps1` printed this on every run:

```text
Kimi    NOT SUPPORTED - Kimi Code has no hook or plugin system (skills + MCP only).
```

v7.7.0 had already disproved the plugin half and wired Kimi natively - and
left this message contradicting it. The hook half does not survive either.
The shipped binary carries an agent hook engine:

```text
PreToolUse    6      const block = await this.runner.triggerBlock("PreToolUse", {
PostToolUse   8
stop_hook            const stopBlock = await this.agent.hooks?.triggerBlock("Stop", {
                     hooks: [...config.hooks ?? [], ...this.plugins.enabledHooks()]
```

Hooks come from `config.hooks` and from every enabled plugin. So the gate
*could* reach Kimi.

What is **not** established is the schema those entries take. The relevant
code is minified into a 129 MB binary and `readHooks(raw["hooks"], ...)` does
not give up its field list to string extraction. So nothing is written.
Guessing a config shape and appending it to a working `config.toml` is the
failure this pack exists to prevent, and Kimi is a provider that currently
works.

The message now says what is true: Kimi has both systems, the plugin is
installed, the hook schema is unverified, and no config is guessed. The
capability is recorded as available and unwired rather than absent.
