# v8.6.10 -- pinning the corpus was only half of it

**2026-08-27.** Based on v8.6.9. **164 canonical skills**, unchanged. A shipped
measurement stopped being true two releases after it was pinned, six
reverse-engineering tools were evaluated, and lean-ctx was measured rather than
quoted.

---

## The number was pinned. The tool moved.

v8.6.8 caught that the rtk savings were measured against `git diff HEAD~3` --
a reference that moves with every commit -- and pinned everything to tag ranges
so the corpus could not drift. That was the right fix for the problem it saw.

rtk then shipped **0.46.0**, which the installer fetched during the `-WithRtk`
test. Re-measured on the same pinned refs:

| command | 0.45.0 | 0.46.0 |
|---|---|---|
| `git diff v8.6.1..v8.6.5` | 87% | **87%** |
| `git log v8.6.1..v8.6.5` | 88% | **88%** |
| `git diff v8.6.4..v8.6.5` | 25% | **25%** |
| `git log --stat -20` | **95%** | **0%** |

Three rows reproduced to the byte. One collapsed: `--stat` now passes straight
through, while plain `git log -20` still compresses 86%. So the flag stopped
being handled somewhere between 0.45.0 and 0.46.0, and the pack shipped a 95%
claim that was no longer reachable.

Pinning the git refs stopped the **corpus** from moving and did nothing about
the **tool** moving. Every number in the rtk table and the catalog note now
carries the version it was measured on, and a contract binds that stamp to the
version `CATALOG.json` declares -- so bumping the declared version without
re-measuring fails the build.

## The first version of that contract was decoration

It asserted `re.search(r"\brtk \d+\.\d+\.\d+\b", rtk_section)` -- "the section
names an rtk version somewhere". Falsifying it by deleting the stamp **passed**,
because the paragraph directly beneath, the one explaining the 0.45.0 -> 0.46.0
regression, still names both versions.

The same shape of mistake as the `HEAD~3` guard two releases ago: an assertion
broad enough to be satisfied by the prose that *describes* the defect. It now
requires the exact stamp `**at rtk <declared>**`, bound to `CATALOG.json`'s
`version` field, and is falsified three ways:

1. stamp removed from the README -> fails
2. stamp removed from the catalog note -> fails
3. **catalog version bumped while the docs stay stale -> fails** (the real case)

## Six reverse-engineering tools, none bundled

| tool | stars | last push | verdict |
|---|---|---|---|
| Ghidra | 72.9k | 2026-08-25 | documented -- GUI, ~1.5 GB |
| GhidraMCP | 9.9k | **2025-06-23** | **rejected -- 14 months stale** |
| GhidrAssist | 710 | 2026-05-29 | documented -- wrong direction |
| radare2 | 24.7k | 2026-08-27 | documented -- best shape of the six |
| Frida | 21.8k | 2026-08-18 | documented -- process injection |
| ImHex | 54.6k | 2026-08-26 | documented -- GUI |

**GhidraMCP is the one that would have mattered**, because it is the only one
that puts an agent in the loop instead of a human. It is also the only one that
fails on maintenance: last commit and last release both 2025-06-23, 82 open
issues, while Ghidra itself shipped through to 12.1.3 in the same period. A
bridge to a fast-moving GUI application, untouched for over a year, is a
liability the pack would inherit.

Four of the six are desktop GUIs. This pack treats GUI tools as user-side -- the
same rule that forbids launching SSEEdit, xEdit or the Creation Kit. **radare2**
has the right shape and is the first pick if the need becomes real. For the
domain this pack serves it mostly is not: SKSE work resolves addresses through
Address Library and CommonLibSSE, which exist so individual modders do not each
re-derive offsets.

Full reasoning, including what each rejection turned on, is in
`docs/TOOL-EVALUATIONS.md`.

## lean-ctx, measured

Carried forward from the 2026-08-26 search as the only candidate claiming
*reversible* compression. **Documented, not bundled.**

Its supply chain is the best of anything evaluated for this pack: `SHA256SUMS`
plus sigstore `SHA256SUMS.sig` and `.pem`. The Windows hash verified on
download.

Its headline **98.1%** is real, and it is a different operation than it reads
as. On a 67,219-byte script:

| mode | bytes | saved |
|---|---|---|
| `-m map` | 2,355 | **96.5%** |
| `-m signatures` | 2,144 | **96.8%** |
| default `read` | 63,905 | 4.9% |
| `-m outline` / `-m summary` / `-m full` | 67,217 | 0.0% |

`map` mode returns `fn pub Install-UabsKimiPlugin() @L1216-1326` -- a **symbol
index, not a compressed file**. That is genuinely useful, and it is exactly what
`codebase-memory-mcp` already provides in this pack, which the
`cbm-code-discovery-gate` hook already forces agents to reach for first.

On the same pinned shell corpus used for rtk and OMNI, through `lean-ctx -c`, it
saved **0.0% on every row**. It carries **78 MCP tools** and ships its own
`tools minimal|standard|power` profiles and a `tools health` "token-budget &
rot" report because of it -- a server that needs its own tool-budget triage is a
poor fit for a pack whose first principle is that MCP schemas are charged every
turn. The binary is 102 MB against rtk's 9 MB.

What is genuinely novel and worth stealing conceptually: **secret redaction on
by default** (`.env` and API keys masked before the model sees them), a path
jail scoped to the project root, and a 223-command shell allowlist. Neither rtk
nor OMNI has anything comparable. Its `gain` command also labels itself "not a
benchmark", which is more honesty than most landing pages manage.

The test binary and its data directory were removed after measuring; nothing was
wired into any agent.
