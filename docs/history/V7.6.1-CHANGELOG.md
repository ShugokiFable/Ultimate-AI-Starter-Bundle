# v7.6.1 — the other 25 places that read a file wrong

v7.6.0 fixed one ANSI-decoding read, the one visibly corrupting the SOUL/AIO
preamble on every install. This finishes the job: 25 more call sites, one of
which was a config-destroying bug that simply had not been triggered yet.

## The bug, restated

On Windows PowerShell 5.1, `Get-Content -Raw` **without** an explicit
`-Encoding` decodes the file using the ANSI codepage — Windows-1252 here, not
UTF-8. A UTF-8 em dash (U+2014, bytes `E2 80 94`) comes back as three separate
characters. Write that string back out as UTF-8 and you have permanent mojibake.

`[IO.File]::ReadAllText` honours the encoding. Every path in this pack is built
with `Join-Path` from an absolute root, so it is a safe drop-in.

## The one that was about to destroy ~/.claude.json

`TOOLS/Add-Reasoning-MCPs.ps1` registers context7, sequential-thinking and
github. Its `Add-ToJsonMcp` read the target with `Get-Content -Raw`, piped it
through `ConvertFrom-Json`, and wrote the object back with `ConvertTo-Json`.

`~/.claude.json` on the test machine contains 26 em dashes. Measured on a real
copy of that file:

```text
broken path : 26 em dashes ->  0   mojibake sequences: 26
fixed path  : 26 em dashes -> 26   mojibake sequences:  0
```

The round trip destroys every one of them. It had not fired only because the
script skips writing when all three servers are already present — so it was one
new server, or one `-Refresh`, away from rewriting the file. Kimi's `mcp.json`
goes through the same function.

The v7.6.0 notes called this risk "latent". That was accurate about the state of
the files on disk and too generous about the distance to failure.

Of these, the read-then-write-same-file sites were the dangerous ones:
`Add-Reasoning-MCPs.ps1` (JSON round trip, and the TOML append at line 207),
`V7-Common.ps1` (the Grok `config.toml` MCP block updater and the
`[compat.claude]` cell writer), `Setup-HouseCarl.ps1`, and
`Install-Completeness-Gate.ps1`. The rest are read-only today, and were swept so
that a future edit which adds a write cannot inherit the bug.

One site is deliberately left alone: section 7 of the pack gate compares
`Get-Content -Raw` against `ReadAllText` precisely to detect a file that would
be corrupted. It now carries an `# ansi-intentional` marker.

Writes were not touched. `Set-Content -Encoding utf8` on PS 5.1 adds a BOM, and
v6 shipped a BOM that made 7 skills undiscoverable and broke PS 5.1 parsing. The
existing `Set-Utf8NoBom` helper and `New-Object System.Text.UTF8Encoding $false`
remain the write paths.

## New gate section 7b

A scan of every `.ps1` in `TOOLS`, `TESTS` and the pack root fails the build if a
bare `Get-Content ... -Raw` returns. Lines carrying `-Encoding`, a leading `#`,
or the `# ansi-intentional` marker are allowed. The pattern is built by string
concatenation so the test's own source cannot match it.

Verified to actually fail, not just to pass: reintroducing the bug at
`Build-Toolbelt.ps1:38` produced

```text
=== 7b. No script reads a file with the ANSI codepage ===
  FAIL ANSI-decoding reads found (use [IO.File]::ReadAllText): Build-Toolbelt.ps1:38
PACK GATE: FAIL (1 problem(s))
```

and the file was restored byte-identical afterwards.
