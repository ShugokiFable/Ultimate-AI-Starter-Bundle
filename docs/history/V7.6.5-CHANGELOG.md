# v7.6.5 — a hook that can hang wedged the whole Grok session

Found by user report: after v7.6.4 made Grok's hooks actually run, a new
failure appeared — when a PreToolUse hook *times out*, Grok stays stunlocked
and the session has to be abandoned.

## Root cause

Two compounding problems, one in the pack and one in the host:

1. **The pack: a hook that could outlive its timeout.**
   `assumption_gate.py`'s drive check probed every letter A-Z with
   `os.path.isdir("X:\\")`. That call touches the device — and a sleeping or
   disconnected network drive (the mapped backup drive this machine actually
   has) blocks it for *seconds per letter*. Twenty-six letters of that is
   far past Grok's 15s hook timeout. The same script also allows up to 2s
   for a stdin read and 10s per git subprocess, with no overall cap.

2. **The host: Grok does not recover from killing a hook.** When the 15s
   timeout fires, Grok terminates the hook process and then wedges the turn
   instead of continuing. That part is Grok's bug and cannot be fixed from
   here — so the fix below makes the first problem impossible instead: the
   hook process is never alive to be killed.

## Fix

**`existing_drives()` no longer touches any device.** It reads the
`GetLogicalDrives` bitmask the session already holds — 6ms measured, down
from seconds-per-dead-drive. Disconnected-but-mapped letters still appear in
the bitmask, which is the fail-open direction: the gate treats them as
existing rather than blocking on them.

**Both gates gained a hard watchdog.** Armed as the very first thing in
`__main__`, a daemon `threading.Timer` calls `os._exit(0)` at 10s for
`--pre` and 25s for `--stop` — comfortably under every host's timeout
(Grok/Claude/Codex allow 15/30, Hermes 20/40). Whatever hangs from now on —
a stalled git on a network repo, a pipe the host never closes, a slow
interpreter cold start on a loaded machine — the process exits quietly and
the host sees a clean pass. Fail open, enforced by physics rather than by
careful code review.

Live copies synced to all three places the gates run from: the
`Skyrim-AI-V5\hooks` install root (serves Claude, Grok and Hermes), the
bundle's Codex plugin source, and Codex's live plugin cache.

## Verification

- `existing_drives()`: `{C, S, Z}` in 6.1ms — Z: included without probing it.
- stdin held open forever (Grok's known behaviour): gate exits on its own at
  2.3s, exit 0.
- Watchdog mechanism: a process hung in `time.sleep(3600)` under the same
  Timer pattern died at its 10s budget, exit 0.
- Detection intact: `xcopy Q:\tools\x.exe .` is still denied, drive letter
  named in the reason.
- Both self-tests PASS.
- Every provider's exact wired command exits 0: Grok's `&`-form, Claude's
  cmd form, Codex's bare-`python` plugin form, Hermes's venv interpreter.

## Not changed

- Hook *logic* — matchers, findings, deny messages, the 2s stdin budget, and
  per-subprocess git timeouts are all as they were. The only behavioural
  change is that a check that used to block on hardware now reads a bitmask,
  and a process that used to trust its own code paths now carries a fuse.
- Hook timeouts in provider configs (15/30/20/40s) — they stay as generous
  outer bounds; the watchdog simply guarantees they never fire.
