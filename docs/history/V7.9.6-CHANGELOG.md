# v7.9.6 — Profiles are scoped to a project, not to the machine

**2026-08-21.** Based on v7.9.5.

7.9.5 built the capability-profile router and then registered every profile
machine-wide. This release makes the code do what three separate documents
already claimed it did.

---

## The defect

`BUNDLED-TOOLS/PROFILES.json` opens with a paragraph explaining why MCP servers
must not be registered globally — tool schemas ride in context on every turn of
every session, and 143 skill bodies cost ~153,000 tokens while the index an
agent reads costs ~5,500. Every profile in the same file then carried:

```json
"scope": "global"
```

So `Set-McpProfile.ps1 -Auto -Path <project>` detected per project and
registered per machine. Enabling `code-deep` for one repository put Serena's
~23 tool schemas into every Claude, Codex, Grok, Kimi and Hermes session on the
box until someone ran `-Disable` by hand.

`CATALOG.json`'s own Serena entry said `"NOT registered globally"`. Both
statements shipped in the same release. The code sided with the field, not the
prose.

It was found the only way a context bill can be found: the user noticed and
disabled the profile manually.

---

## What each provider actually supports

Checked against the installed CLI, not recalled. Every claim below was produced
by running the tool.

| provider | version | project-scoped MCP | how it was established |
|---|---|---|---|
| Claude Code | 2.1.237 | **yes** — `projects["<abs path>"].mcpServers` in `~/.claude.json` | `claude mcp add --scope local` wrote exactly there; `claude mcp list` in that directory read it back |
| Grok | 1.0.5 | **yes** — `<project>\.grok\config.toml` | `grok mcp add -s project` documents that path |
| Codex | 0.147.0 | **no** | a `.codex/config.toml` placed in a project was absent from `codex mcp list` run inside it; `codex mcp add` has no scope flag |
| Kimi | kimi-code | **no** | `kimi doctor` in a project holding `.kimi-code/mcp.json` reported only the home configs |
| Hermes | — | **no** | `hermes mcp add` has no scope option; the config is one file |

Claude Code's project `.mcp.json` is the other option and was rejected: it puts
a file in the user's repository and raises a trust prompt. The local scope does
neither.

For the three providers with no project scope, the server is **skipped and the
reason printed**. Registering them machine-wide behind a comment that says
"project-scoped" is the bug this release exists to remove. `-Global` is the
explicit opt-in and states the cost.

## Changes

### `code-deep` → `code-intel`

The old name promised depth. The profile holds one server. The old id still
resolves everywhere — state files, scripts and habits that name it keep working.

`team-harness/code-deep` was **not** added. Serena plus the existing
`codebase-memory-mcp` remain the code-intelligence stack until something else is
benchmarked against them.

### Every profile is project-scoped

`scope: "global"` is gone from all six. Nothing in the catalog is useful outside
the project that triggers it; a server that were would belong in the always-on
core instead. The field is still read, so a future server can declare `global`
and mean it.

### Serena is told which project

Verified against the installed Serena 1.7.0's own `--help`:

- project registration gets `--project <absolute path>`
- a `-Global` registration gets `--project-from-cwd` instead — upstream's flag
  for exactly this, described there as "Intended for CLI-based agents like
  Claude Code, Gemini and Codex"

A baked absolute path in a machine-wide config would activate that one project
in every unrelated session, which is worse than not knowing. Per-client
`--context` (claude-code / codex / grok, `agent` for Kimi and Hermes) is
unchanged.

`--enable-web-dashboard false` is kept. Upstream recommends leaving the
dashboard enabled and setting `--open-web-dashboard false`; this pack does not
start a local HTTP listener a user did not ask for, and uses
`TOOLS\Test-McpHandshake.ps1` for diagnosis instead.

### Installed is not enabled

`-List` now says which, per profile, per project:

```
[on ] code-intel     Language-server-accurate code navigation and editing
       enabled for  Z:\code\my-app  -> Claude, Grok
       serena           installed and ready
[off] cloud          Supabase project management
       supabase         SUPABASE_ACCESS_TOKEN is not set
```

An `auto_install` makes a tool exist on disk. It never registers it anywhere.

### Migration

State moves from the flat v1 shape (one `path` per profile) to a per-project v2,
because a profile can now be on for several projects at once and `-Disable` has
to reach every one of them.

The upgrade **moves** the old registrations rather than renaming them in a state
file: it removes the machine-wide entries from every provider config, then
re-registers for the project the state recorded. Only ids this pack recorded as
enabled are touched — a server someone registered themselves is not in the state
file and is left alone. A recorded project that no longer exists is reported and
left off, never re-registered blind.

## Six defects found while building it

Each is reachable by a user; none is specific to the scope change.

**`Get-ClaudeDesktopConfigPath` crashed on an unresolvable folder.**
`[Environment]::GetFolderPath('LocalApplicationData')` returns the **empty
string** when the folder does not exist — documented behaviour of the default
`SpecialFolderOption.None`, not an error — and the next `Join-Path` threw
`Cannot bind argument to parameter 'Path' because it is an empty string`,
killing the whole run inside a helper whose only job was to answer "is Claude
Desktop installed". Reproduced with a child `powershell.exe` whose `USERPROFILE`
had no AppData tree. It reads `%APPDATA%` / `%LOCALAPPDATA%` first now — the way
every other path in this pack resolves — and returns "not installed" when
neither resolves.

**A successful install was treated as fatal.** `uv tool install serena-agent`
prints `serena-agent is already installed` on **stderr** and exits 0. The
auto-install piped stderr into the pipeline under
`$ErrorActionPreference = 'Stop'`, so every re-run on a machine that already had
Serena died with a `NativeCommandError`. It judges the exit code now.

**An identical rewrite counted as a change.** Both add paths rewrote a
byte-identical entry, reported it as a change, and took a timestamped `.bak`
copy — which, for Grok's project config, dropped one backup file into the user's
repository per install run. Identical is now a no-op, and removal collapses the
blank lines it used to leave behind.

**`-Disable` with no `-Path` swept the current directory.** The cwd is a fine
default for "which project am I setting up". It is never a default for "turn
this off": `Set-McpProfile.ps1 -Disable code-intel` run from anywhere pointed at
that anywhere, removed nothing, and deleted the state that knew where the real
registrations were. With no `-Path` it now disables every project the profile
was enabled for.

**An unmounted drive was fatal, twice over.** `Test-Path` does not answer
`False` for a path on a drive that is not mounted — it writes
`Cannot find drive. A drive with the name 'Z' does not exist.`, and every script
here runs with `$ErrorActionPreference = 'Stop'`, which makes that fatal.
`Join-Path` does the same, because it asks the provider to resolve the base,
inside a function whose whole job is string concatenation. A recorded project on
a removable disk, a network share, or simply another machine's drive letter
reaches that state; the tools on this pack's development machine live on `S:`
and its projects on `Z:`, and neither is the system drive. Both are swept: 37
`Test-Path` call sites go through a guarded `Test-V5Path`, and 26 `Join-Path`
calls through `Join-V5Path`, which uses `[IO.Path]::Combine` and never touches
the filesystem. A release contract fails the build if a new one appears.

CI found it, and found it because the test that provoked it broke its own rule:
it seeded a stale project at a hardcoded `Z:\gone\missing`, and the runner has
no `Z:`. The test now asks the system which drive letters are free.

One more, caused by the fix rather than found by it: once an identical rewrite
stopped counting as a change, a second `-Auto` run recorded nothing and marked
the profile off while the server was still registered. State records
**registration**, not whether this particular run moved any bytes.

## Verification

`TESTS/Test-McpProfiles.ps1` gained a section that drives the real
`Set-McpProfile.ps1` against a sandboxed `USERPROFILE`, `LOCALAPPDATA` and
`APPDATA`, then reads the provider configs it produced. Every check in it fails
against 7.9.5.

- a clean install leaves Serena unregistered machine-wide
- `-CheckOnly` writes nothing, and creates no project config
- a detected project gets Serena, with `--project <that path>` and the
  provider's own `--context`
- the machine-wide Claude, Grok, Codex and Kimi configs stay clean
- an unrelated project has no entry, and no `.grok` directory appears in it
- a repeat run duplicates nothing, rewrites nothing, leaves no `.bak` litter,
  and still reports the profile as registered
- `-Disable` with no `-Path` reaches the project it was enabled for, in both
  Claude and Grok, and leaves unrelated servers alone
- the old `code-deep` id still resolves
- `-Global` registers machine-wide, uses `--project-from-cwd`, does not bake a
  path, reaches Codex, and says what it costs
- a `{project}` command (Unity) is refused machine-wide; Serena is not
- upgrading a 7.9.5 machine drops the machine-wide Claude and Codex entries,
  keeps unrelated Codex servers, re-registers for the recorded project, and
  rewrites the state file in the new shape under the new id
- a recorded project that no longer exists is reported, not re-registered, and
  does not fall back to machine-wide
- the Grok ceiling counts the union of the user and project config files, and
  counts a server declared in both once

Gate total: 49 new checks, `MCP PROFILE GATE: PASS`.

### On the machine, not only in the sandbox

`TOOLS\Test-McpHandshake.ps1` learned `-Path <project>`, because a diagnostic
that reads only the machine-wide config is blind to every server this release
moved — and its cost line was reporting a total no real session pays. Run
against this pack's own repository after enabling `code-intel` for it:

```
Claude, machine-wide only      9 servers    188 tool schemas every turn
Claude, in this project       10 servers    209   (serena [project]  21 tools)
```

`~/.claude.json`'s top-level `mcpServers` is unchanged at eight; the Serena
entry is under `projects["Z:\...\Ultimate-AI-Starter-Bundle"].mcpServers` with
`--context claude-code --project <that path>`. `~/.codex/config.toml`,
`~/.grok/config.toml` and `~/.kimi-code/mcp.json` contain no `serena` at all.
Grok declined it: that machine sits at the documented six-server budget, and the
router said so by name rather than pushing it to seven.

`.grok/` and `.serena/` are gitignored and excluded from the manifest generator —
this repository is itself a project the router can be pointed at, and an
untracked `.grok\config.toml` would fail its own manifest verifier.

## Not in this release

No new skills. 144 canonical, mirrored across five provider trees, unchanged —
this release is capability routing and context cost, and adding reasoning skills
to raise a count would be neither.
