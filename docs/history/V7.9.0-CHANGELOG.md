# v7.9.0 — the fresh install never worked, and every gate was green

7.8.0 passed 16/16 release contracts, a 10-section Windows pack gate, a Hermes
bootstrap contract, deterministic double-built archives and full manifest
verification. It shipped 142 (then 143) skills that told an agent to verify
before claiming completion.

It could not install itself.

## `$contract.compatible` does not exist

`TOOLS/Install-SkyrimForge.ps1`, the step that provisions the bundled Forge and
wires it into all five providers, ended:

```powershell
$contract = $contractRaw | ConvertFrom-Json
if (-not $contract.compatible) { throw "Forge reports incompatible bundle contract for $BundleVersion." }
```

`forge bundle-contract --bundle-version 7.8.0` returns:

```json
{
  "bundle_version": "7.8.0",
  "contract_version": 1,
  "forge_version": "5.2.0",
  "product": "Skyrim Forge",
  "reason": "Compatible",
  "result": "PASS",
  "supported_bundle_range": ">=7.8.0,<8.0.0"
}
```

There is no `compatible` key, and there never has been in any released Forge.
`$contract.compatible` is `$null`, `-not $null` is `$true`, so the `throw` fired
on every run. `INSTALL-V7-AIO.ps1` wraps the call in:

```powershell
if ($LASTEXITCODE -ne 0) { throw "Skyrim Forge 5.2.0 installation/contract failed with exit code $LASTEXITCODE." }
```

so the whole all-in-one install aborted at the Forge step, after the providers
were bootstrapped but before the completeness gates, the reasoning MCPs, the
toolbelt and the final doctor.

### Why nothing caught it

Two files, both individually tested, whose *agreement* nothing tested. The
contract suite checked that the installer existed and that the payload was
present. Forge's own suite checked that the contract returned `PASS`. No test
read one file's field name against the other file's output.

The new gate does exactly that, and nothing else:

```python
checked = set(re.findall(r"\$contract\.([A-Za-z_][A-Za-z0-9_]*)", installer))
emitted = set(re.findall(r'^\s+"([a-z_]+)":', contract_src, re.M))
unknown = sorted(f for f in checked if f not in emitted)
assert not unknown
```

It reads the contract source out of the bundled ZIP, so it tests the Forge the
user will actually receive.

## The install directory carried its version

Every provider stores an MCP server command as a hard absolute path, in its own
format — Claude JSON, Kimi JSON, Codex TOML, Grok TOML, Hermes YAML. A
version-stamped install directory renames itself on every upgrade, so each
upgrade disconnects whichever configs were not rewritten. It never errors: a
provider that cannot spawn its server just shows no tools.

Live state when this audit started, three paths and no two agreeing:

```text
SKYRIM_FORGE_ROOT       S:\Apps\Skyrim Tools\Skyrim-Forge-5.1.6    deleted
all five provider MCPs  S:\Apps\Skyrim Tools\Skyrim-Forge          never created
actually on disk        S:\Apps\Skyrim Tools\Skyrim-Forge-5.2.0    no virtualenv
```

`TOOLS/Repair-McpPaths.ps1` exists to walk five config formats and repoint dead
absolute paths afterwards. That is a symptom treated well. The cause is that the
directory name changes at all.

**The archive keeps its version. The install directory never does.** The
installer resolves one versionless root, and when it finds a version-stamped
install it *moves* that onto the versionless name rather than extracting a
second copy beside it. `TESTS/Test-ForgeRootResolution.ps1` drives
`Install-SkyrimForge.ps1 -ResolveOnly` against synthetic layouts and proves:

| case | assertion |
|---|---|
| `Skyrim-Forge-5.2.0` present | migrates to `Skyrim-Forge`, contents preserved |
| after migration | the stamped directory is **gone** — moved, not copied |
| root points at a deleted version | finds the live sibling and migrates it |
| 5.1.0 / 5.2.0 / 5.10.0 all present | keeps **5.10.0** — version compare, not string |
| anything | the resolved root never ends in `-x.y.z` |
| installer source | contains no `Skyrim-Forge-x.y.z` literal in code |

## Skyrim Forge 5.2.1

`forge --help` printed *"Skyrim Forge 4.2 Automation Fabric"*, the GUI window
title said the same, and the Go native self-test wrote a `4.2` fixture string —
all from inside a 5.2.0 install.

Forge already had a version gate. It compared eight enumerated sources
(`version.py`, `pyproject.toml`, `CURRENT.txt`, `VERSION.txt`, `START-HERE.bat`,
`README.md`, the Go constant, the skill series) and they all agreed. None of the
three offenders was on the list, and enumeration cannot find what it does not
enumerate.

The gate now also sweeps every shipped `.py`, `.ps1`, `.bat` and `.go` file for
a product-name literal carrying a major.minor, and fails on any that is not the
current series. Proved by reintroducing the `4.2` literal:

```text
stale product-version literal in shipped source: skyrim_forge/cli.py:15 says 4.2, series is 5.2
```

`tests/test_bundle_contract_v520.py` also hardcoded `"5.2.0"`, so every patch
release was a test edit. It pins the 5.2 *series* now — the thing the contract
range actually promises.

Native helpers were rebuilt under the pinned Go 1.23.2 profile; the repository
validator passes and is idempotent across three runs; the release archive builds
byte-identically twice.

## `skyrim-forge-bridge` removed

143 canonical skills to 142.

The skill described "Skyrim Forge Bridge 0.2.x", resolved from a
`SKYRIM_FORGE_BRIDGE_ROOT` environment variable, and stated:

> It does not write ESP/ESL/ESM records, compact FormIDs, author VMAD, drive
> Creation Kit, or replace semantic plugin validation.

None of that is true of the Forge this bundle installs. A skill that contradicts
the tool actually present is worse than no skill, because the agent believes it
and stops reaching for a capability it has.

It also shipped a script that could not run anywhere:

```powershell
[string]$Forge = "$HOME\Documents\Apps\skyrim-forge-bridge\.venv\Scripts\skyrim-forge.exe"
```

`run_forge_audit.ps1` now resolves `SKYRIM_FORGE_ROOT`, tries the versionless
form of every candidate, falls back to the installer's default root, and runs
`forge doctor` then `forge plugin-info`. Four skills that referenced the bridge —
`ai-tooling-stack`, `skyrim-plugin-authoring`, `skyrim-ship-gate`,
`skyrim-tool-router` — now point at `forge`.

Two dangling pointers to `references/_CORPUS_STATUS.md`, a file that has never
shipped, were removed from `dialogue-authoring` and `kid-authoring`.

**Nothing else was cut.** The 57 reliability skills 7.8.0 added were read and
kept: `check-work`, `artifact-proof`, `artifact-provenance` and
`adversarial-self-review` overlap, but each has a distinct trigger and a
distinct payload, and deleting good skills to reach a smaller number is not the
same as removing dead ones. Always-on tier-1 metadata is ~7.4k tokens for 142
skills.

`.github/scripts/check_versions.py` had never looked at either `.bat` title, so
both sat at `v7.8.0` for the whole release. `test_version_sources` covers them
now.

While fixing the builder's Forge literal, `verify()` was left referencing a
`root` it did not receive — a `NameError` on every release build. It takes
`root` explicitly now and checks the **extracted** archive for a Forge payload
and a matching `VERSION.txt`, rather than checking the source tree it was built
from.
