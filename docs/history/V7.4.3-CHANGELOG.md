# V7.4.3 CHANGELOG — the limit is 8 running, and a plugin was eating a slot

2026-08-16

v7.4.2 said "keep Grok at five MCP servers or fewer". Wrong again, and for a
familiar reason: I measured 5 (fine) and 7 (wedged), **never tested 6**, and
called it a limit. Worse, the working 5-set excluded three servers while the
broken 7-set excluded only one — so "it is the count" was an inference, not a
result.

## What the boundary actually is

Testing every 6-server and 7-server composition instead of assuming:

```text
6 configured  x5 different sets  -> ALL OK  (5.6-24.9s)
7 configured  x4 different sets  -> ALL WEDGED
```

Composition is irrelevant — sets that swapped every member behaved identically.
So it is a count, but the number is not 5 or 6.

## The free-rider

Counting grok's direct child processes during a wedged run showed **8** servers,
not 7. The extra one:

```text
node.exe -e "const f=require('fs')..."   <- mcp-search, from the claude-mem plugin
```

**`[compat.claude] mcps = false` does not stop plugin-provided MCP servers.**
Every enabled Claude Code plugin with a `.mcp.json` still loads, and never
appears in `config.toml`, so it is invisible to any count you do by reading the
config.

Proved by hiding one file — same 7 configured servers either way:

```text
7 configured + mcp-search        -> 8 running -> WEDGED
7 configured, mcp-search hidden  -> 7 running -> OK, 7.3s
```

**The limit is 8 running servers. Seven is fine.** With claude-mem enabled that
leaves **6 configured**; disable MCP-providing plugins and it is 7.

## Changes

## Four corrections, one habit

7.3.1 (orphan fleets), 7.4.0 (`tool_count`), 7.4.2 (five servers) — plus Rule 1
back in 7.3.0. Every one of them was something *adjacent* to the behaviour
mistaken for the behaviour: a process list, a counter, a boundary I never
probed. Each died in minutes once tested directly. The cheat-sheet now leads
with that, and the fix for this class of error is not "be more careful", it is
**test the untested case before naming a limit**.
