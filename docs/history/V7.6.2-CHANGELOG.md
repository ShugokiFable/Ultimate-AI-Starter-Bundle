# v7.6.2 — the repair tool would have corrupted a config, and CI now exists

Two things, one embarrassing and one overdue.

## Repair-McpPaths produced invalid JSON

`TOOLS/Repair-McpPaths.ps1` deliberately does not parse the five config formats.
It finds the dead path as a literal string and swaps it, which cannot reorder or
reformat a user's file. That is still the right approach — but it missed that
**a JSON config does not store the path as written**. `~/.kimi-code/mcp.json`
holds:

```json
"command": "S:\\Apps\\Skyrim Tools\\Skyrim-Forge-5.1.3\\.venv\\Scripts\\python.exe"
```

Every separator is doubled. The tool matched that doubled literal, resolved it
against the filesystem (where the doubling is not a real path), and wrote back a
replacement at a different escaping level. Two successive attempts got it wrong
in opposite directions:

```text
attempt 1:  S:\Apps\Skyrim Tools\Skyrim-Forge-5.1.4\.venv\\Scripts\\python.exe   (mixed)
attempt 2:  S:\\\\Apps\\\\Skyrim Tools\\\\Skyrim-Forge-5.1.4\\\\...              (quadrupled)
```

Either one makes `mcp.json` unparseable. This was caught only because the tool
defaults to report-only and prints its replacement before writing — the dry run
is load-bearing, not a courtesy.

Two fixes:

- `Get-NormalPath` collapses runs of separators, so the filesystem check and the
  version splitter see a real path instead of empty segments.
- `ConvertTo-ConfigLiteral` re-applies whatever escaping the original literal
  used, with `String.Replace` rather than `-replace`. PowerShell's `-replace` is
  a regex on **both** sides, and counting backslashes through two layers of
  escaping is exactly how both wrong attempts happened.

Gate section 8 now asserts all three cases — JSON keeps doubled separators,
TOML/YAML keeps single ones, and an end-to-end round trip confirms the repointed
JSON still parses back to the live path.

## This repo had no CI

Three jobs, all `windows-latest`, all `shell: powershell`:

- **Pack gate** — runs `TESTS\Test-V7-Pack.ps1`, all nine sections. The job
  asserts `$PSVersionTable.PSEdition -eq 'Desktop'` first, because the pack
  targets **Windows PowerShell 5.1** specifically: its ANSI-codepage default,
  its BOM behaviour and its native-stderr handling are the origin of most bugs
  this pack has shipped (v7.5.6, v7.6.0, v7.6.1). Running the gate under
  PowerShell 7 would test a different language and pass while 5.1 breaks.
- **MANIFEST** — re-hashes every recorded file. `.gitattributes` sets `* -text`
  so a clone is byte-identical to the released pack; this fails if checkout ever
  starts normalising line endings, which would silently invalidate every hash.
- **Version consistency** — the pack version is restated in seven places that
  cannot read each other. v7.5.3 shipped with `CATALOG.json` still declaring
  6.8.0, seven minor versions behind, because nothing checked. Now the installer
  banner, the installer state string, `README.md`, `START-HERE.txt`,
  `CATALOG.json`, `VALIDATION.json`, the `CHANGELOG.md` section and the
  `docs/history/` entry must all agree with `VERSION.txt`.

## Verification

`TESTS\Test-V7-Pack.ps1` — **PACK GATE: PASS**, 9 sections.

The three new section-8 assertions fail against v7.6.1's tool: it emitted a
mixed-escaping path that `ConvertFrom-Json` rejects.

Both CI helper scripts were run locally before being committed, against the real
tree rather than trusting them to work on first push.
