# v7.9.7 — Stop assuming: evidence closure

**2026-08-21.** Based on v7.9.6.

The objective is not more tools or more skills. It is to turn

```
guess -> edit -> hope
```

into

```
observe -> verify -> understand -> edit -> run -> observe again -> finish
```

without making every simple task expensive.

---

## The audit came first

The prompt for this release asked for a "stop assuming" skill. The bundle
already had eleven skills covering that ground — `assumption-audit`,
`research-verification`, `observability-first`, `systematic-debugging`,
`verification-before-completion`, `artifact-proof`, `real-boundary-testing`,
`tool-output-awareness`, `source-of-truth`, `process-lifecycle-cleanup`,
`secret-hygiene` — so each was read before anything was written.

Exactly one behaviour had no owner: **does the rendered result actually look
right**. Nothing in 144 skills asked that question. So one skill was added and
the rest were extended at their own seams rather than cloned.

| skill | now also owns |
|---|---|
| `visual-verification` | **new** — appearance is verified by looking at the rendered output |
| `observability-first` | software the agent *writes*, so its next failure produces evidence |
| `secret-hygiene` | proving a variable is set without printing its value |
| `research-verification` | an explicit tool ladder, and the counterweight: do not browse reflexively |
| `verification-before-completion` | rendered output and runtime behaviour as evidence rows; freshness |
| `assumption-audit` | routing — which skill settles the assumption you just named |

145 canonical skills, mirrored across five provider trees.

## "Use vision" is unfalsifiable, so it ships a canary

A model that cannot see pixels can still write *"I inspected the screenshot and
it looks correct"*. The honest report and the fabricated one are the same
sentence, and no wording in a skill file separates them. These are two different
claims:

```
a screenshot was captured        <- a file exists
the agent inspected the pixels   <- a model actually read the image
```

So the pack ships a check instead of an instruction.
`TOOLS/vision-canary/vision-canary.png` contains a word, a shape and a colour;
the expected answer exists only as a SHA-256, so reading the repository is not a
substitute for looking. `TOOLS\Test-VisionCanary.ps1` answers PASS or FAIL, and
a FAIL is an answer, not an error:

> visual verification unavailable in this provider/session

...keep the screenshot as an artifact, fall back to DOM/console/geometry, and
name what stays unverified.

## Eight fixtures for the behaviour itself

`TESTS/evidence-scenarios/` — because "does SKILL.md contain the word
screenshot" is document compliance, not behaviour.

| | scenario | what it separates |
|---|---|---|
| A | a fixed header covering the page heading | rendered output vs. valid-looking source |
| B | grey boxes that are 404s | console/network evidence vs. guessing at CSS |
| C | a crash whose log already names the cause | reading the log vs. guessing from the symptom |
| D | the same crash with nothing to read | targeted instrumentation vs. speculative edits |
| E | a version-specific Serena flag | asking the installed binary vs. recall |
| F | `list.append()` returns what? | **not** researching what cannot change the answer |
| G | a screenshot on a client with no vision | honest limitation vs. fabricated inspection |
| H | a token in the environment | proving presence vs. printing the value |

Each has a rubric. Scoring an agent is a judgement; scoring the **fixture** is
not, so `check_fixtures.py` proves each one still exhibits its defect and is
chained into the pack gate — a benchmark whose defects have quietly been
repaired passes every provider and measures nothing.

**Scenario A was run for real.** The page renders with "Order summary" clipped
behind the fixed header and the fine print at roughly 2.3:1 contrast. Every CSS
rule in it is individually valid; no DOM query reports a problem.

## Cleanup that 7.9.6 left

### Supabase is withdrawn

It was the only profile requiring an account and a personal access token,
against this pack's default of free, local, keyless and no signup. Removed from
`PROFILES.json`, `CATALOG.json`, the skill and the docs — and **not** replaced
with another account-dependent backend.

Removing a profile from a catalog does not un-register it from a machine, so
`Set-McpProfile.ps1` now carries a withdrawn-profile migration: it un-registers
the server ids **this pack recorded**, in the scopes it recorded them, and drops
the state. A `supabase` server configured independently is not in that state file
and is never touched — proven in the gate by a fixture that has both.

A release contract now fails the build if any profile server declares an API key.

### Blender

Three things, each verified upstream rather than recalled:

- **Pinned.** `uvx blender-mcp` was the one unpinned invocation in the catalog.
  PyPI's current release is 1.8.3 (uploaded 2026-08-16), and
  `uvx blender-mcp@1.8.3 --help` runs — so the pin syntax is proven.
- **Discovered, not hardcoded.** 7.9.6 shipped
  `S:\Steam\steamapps\common\Blender\blender.exe` — this maintainer's own drive,
  which cannot match on anyone else's machine, in a pack whose own rule is that a
  drive letter is never assumed. Replaced with what
  `uvx blender-mcp@1.8.3 addon-paths` actually reports:
  `%APPDATA%\Blender Foundation\Blender\<ver>\...`, which Blender creates on
  first run whatever the install source, Steam included.
- **Telemetry, stated rather than claimed.** Read from the 1.8.3 wheel: the
  bundled addon has a `telemetry_consent` preference and attaches its
  edit-capture handlers only with consent, and contains **no telemetry
  endpoint** (its outbound URLs are PolyHaven, Rodin and Sketchfab, each
  separately toggled). There is no server flag to pass and nothing outside the
  editor can set it — so the note says that, instead of claiming a disable.

A new contract fails the build on any drive letter or literal user directory in
a shipped config. There was already a check for skill scripts; the data files it
did not cover are exactly where this happened.

## sequential-thinking loses its always-on slot

The pack has counted **tools** since 7.9.5, and by that unit sequential-thinking
was the cheapest server it shipped: one tool, against houseCARL's 45 and Forge's
52. It never looked like a candidate.

Tools is the wrong unit. Speaking real MCP to both always-on npx servers:

```
sequential-thinking   1 tool    4,587 bytes   ~1,146 tokens every turn
context7              2 tools   4,870 bytes   ~1,217 tokens every turn
```

One tool, costing as much as context7's two — on every turn of every session, on
every provider, for a structured scratchpad rather than a capability. It fetches
nothing and reaches nothing the model could not write in its own reasoning,
while this pack ships decomposition skills that cost nothing until they match
and every provider it targets has native reasoning. (The Codex run in this same
release announced "reasoning effort: high" before it did anything.)

context7 keeps its slot on the same evidence: 1,217 tokens buys current
documentation for a library the model would otherwise answer from memory. That
is a capability, not a restatement.

So it moved out of always-on and **was not deleted**. It is the `reasoning`
profile: `scope: global`, because a thinking aid is not a property of a project,
with **no detection markers** so `-Auto` can never turn it on.

```powershell
TOOLS\Set-McpProfile.ps1 -Enable reasoning -Global   # keep it
TOOLS\Set-McpProfile.ps1 -Disable reasoning          # give the tokens back
```

Machines that already have it are **told, not edited** — with the number and
both commands. A server someone has been using does not vanish because a
measurement went the other way.

**Not measured:** whether it improves weaker models enough to justify the cost.
That needs a benchmark across Grok, Kimi and Hermes this release did not run.
The honest consequence of not having that number is to stop paying by default
rather than to keep paying by default.

## A finding nobody was looking for

A real `codex exec` run in this repository printed:

```
warning: Exceeded skills context budget. All skill descriptions were removed
and 23 additional skills were not included in the model-visible skills list.
```

This pack routes **by description**. With every description removed, that
mechanism is gone on Codex and the model sees a list of bare names.
`codex features list` shows `skill_search` already `stable true`, so it is not a
missing flag — the static index is simply over budget. Measured here: 215 skills
in `~/.codex/skills`, 38,228 characters of name+description (~9.5k tokens), of
which the pack supplies 145 / 26.8k.

The doctor cannot raise Codex's budget, and trimming 145 descriptions to fit one
provider would degrade routing on the other four. What it can do is stop the
failure being silent: the installed-state doctor now reports the measured size
and the remedy. **This is a limitation, not a fix** — carried into the next
release with numbers attached.

## Also fixed

**The accepted CodeQL autofix did not compile, and main was red.** CodeQL
flagged `"(?:`.|[^"\r\n])*"` as py/redos correctly — measured at **3,684 ms** on
an unterminated string with 26 escapes. The suggested fix deleted the group's
closing parenthesis, which is `re.error: missing ), unterminated subpattern`;
eight Forge jobs died at import. Restoring the parenthesis made it compile and
left the blowup exactly where it was (**3,571 ms**) — *and* reordered the
alternation so an escaped quote `` `" `` ends the string instead of continuing
it, changing what the validator parses on ten lines of this repository.

The repair is to make the branches **disjoint**: the escape branch starts with a
backtick, so the ordinary branch excludes it. One way to match any input,
nowhere for the blowup to come from, **0 ms**, and identical matches to the
pre-autofix behaviour across all 68 PowerShell files here.
