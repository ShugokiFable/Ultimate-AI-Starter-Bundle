# v7.9.9 — Truthful capability routing

**2026-08-22.** Based on v7.9.8.5.

A narrow corrective release. The goal was to make the bundle's tool-routing
claims match what a genuinely clean machine can do, and to apply the pack's own
*stop assuming* rule to the pack itself.

146 canonical skills, mirrored across five provider trees. No new skills, no new
always-on MCP, and one server that `-WithExtras` used to register now waits for
the key that makes it worth carrying.

---

## The claim under review was mine

v7.9.8 said Hermes v0.20.4 ships keyless `web_search` / `web_extract` over a
five-vendor ring. The brief for this release said that was overbroad: Hermes'
Firecrawl provider is only *available* with `FIRECRAWL_API_KEY` /
`FIRECRAWL_API_URL` or the Nous gateway, so the capability should not be
described as keyless.

The v7.9.8 evidence had a real weakness. It called
`plugins.web.keyless_mcp` helpers **directly**, which proves the function works,
not that resolution ever reaches it — and it ran on a developer machine, which
is not evidence about a new user.

So it was re-run properly: an isolated `HERMES_HOME`, and every environment key
containing FIRECRAWL / NOUS / EXA / TAVILY / PARALLEL / BRAVE / SEARXNG /
KEENABLE / SERPER / BROWSERBASE removed before importing anything.

```
all five ring vendors, no credentials
  exa        search PASS 1.1s   extract PASS 0.3s
  parallel   search PASS 1.7s   extract PASS 1.6s
  tavily     search PASS 1.2s   extract PASS 1.0s
  firecrawl  search PASS 1.6s   extract PASS 0.3s
  keenable   search PASS 0.5s   extract PASS 0.3s

the user-facing tool
  web_search_tool  -> 1.9s, real results, served_by keenable
```

And the extraction genuinely renders — native keyless extract against a plain
`urllib` fetch, same clean environment:

```
tradingview.com/symbols/BTCUSD   39,437 chars vs 12,535   (3.1x, 0.4s)
react.dev/learn                  18,988 chars vs 15,101   (1.3x)
```

**The claim holds.** Hermes already has rendered extraction at zero permanent
schema cost, and v7.9.8's decision not to register firecrawl-mcp stands.

### The reviewer was half right, and the half matters

`is_available()` really does return False without credentials. It is the
**keyed** path:

```python
def is_available(self) -> bool:          # plugins/web/firecrawl/provider.py
    return check_firecrawl_api_key()

def is_keyless_available(self) -> bool:
    return keyless_enabled() and provider_tier("firecrawl") != "paid"
```

The registry's resolution walk calls the second one for the free tier. Reading
only the first says the capability is missing; reading only the second oversells
it. Both are now documented next to each other, because quoting either alone
produces a confident wrong answer.

### An independent check found what I had missed

An adversarial verification reproduced every result above and then broke
something I had asserted. Hermes recognises throttling by **string matching**:

```python
_RATE_LIMIT_MARKERS = ("rate limit", "rate-limit", "ratelimit",
                       "too many requests", "429", "quota exceeded", "slow down")
```

Tavily's keyless cap says `hourly_cap_reached`, which is in none of them. The
ring treats it as permanent and **stops walking** while four vendors are still
answering — measured at ~15% hard failures on the default path during a cap
window, and 100% if `web.backend` is pinned to tavily. Bursting 30 concurrent
requests at bare Exa produced 27 HTTP 429s; the same burst through the ring
served 30 of 30.

That is an upstream defect in Hermes 0.20.4. This pack does not patch installed
tools, so it is documented rather than claimed away, and the wording everywhere
changed from "rate-limit failover" to **"failover on recognized rate-limit
responses"**.

## Firecrawl MCP, measured tool by tool

Every one of the 25 advertised tools called with the credential environment
scrubbed:

```
KEYLESS     2   firecrawl_scrape, firecrawl_search
NEEDS_KEY  21   Unauthorized: API key is required
DEPRECATED  1   firecrawl_extract -- "deprecated and unavailable through MCP"
UNVERIFIED  1   firecrawl_parse -- requires a self-hosted FIRECRAWL_API_URL
```

The record that ships was regenerated later, after these sweeps had spent the
free daily allowance, so it reports those same two tools under `rate_limited`
rather than `keyless`. That is not a different answer: **being throttled proves
the tool was reached without credentials** -- you cannot exhaust a free tier you
cannot access. The generator emits `keyless_capable` (keyless + rate_limited)
for exactly this reason, and that is the field documentation and contracts
compare against, so the same capability reports identically whether or not the
sweep happened to run inside a spent quota window.

Two consequences worth stating plainly:

- The catalog's note read *"scrape/search/interact work on the keyless hosted
  tier; crawl/map/agent/extract need a key."* **Two of those five claims were
  false.** `interact` answers *Unauthorized*, and `extract` is not key-gated at
  all — it is gone. Nobody had ever called the tools; the note came from a
  vendor page and then aged.
- Firecrawl's own MCP instructions say Search, Scrape **and Parse** are free
  without authentication. Parse is not, on this pinned server.

### So the note is generated now

`TOOLS/measure_mcp_capability.py` calls every advertised tool with credentials
scrubbed, derives arguments from each tool's own `inputSchema`, and writes
`BUNDLED-TOOLS/capability-records/<id>.json`. A release contract compares the
catalog's `keyless_tools` against that record.

It keeps five verdicts apart, and two of those separations were learned the hard
way in this release:

- **UNVERIFIED is not KEYLESS.** The first cut counted nine argument-validation
  failures as working keyless tools. A call that never reached the auth check
  says nothing about auth.
- **RATE_LIMITED is not NEEDS_KEY.** Two full sweeps exhausted the free daily
  allowance, and the throttle message is:

  > The free daily limit for this network has been reached; try again in about
  > 71901 seconds. To continue now: ... update the Firecrawl server entry so its
  > URL is ...mcp-oauth...

  It recommends OAuth. A classifier matching auth words first files a working
  keyless tool as needing a key — which is precisely how this tool contradicted
  a correct measurement taken twenty minutes earlier. Throttle markers are now
  checked **before** auth markers, and the ordering carries a comment saying why.

## Registration is a choice, not a side effect

`-WithExtras` used to register firecrawl-mcp on a keyless machine and mention it
in one line. Measured, that bought **2 usable tools out of 25 for ~9,080 tokens
on every turn**, duplicating a native capability.

It is an mcp-npx component, so registering IS installing -- npx resolves the
package on first launch either way, and nothing is cached by registering it
early. The entry simply waits:

```
firecrawl-mcp: NOT registered (no FIRECRAWL_API_KEY)
     Keyless this server is 2 usable tools out of 25 ...
     Enable: setx FIRECRAWL_API_KEY "<key>" then re-run with -WithExtras
     Or register it keyless anyway: -WithExtras -RegisterKeylessExtras
```

Declared in the catalog (`keyless_registration: skip`), not hardcoded, so the
next component with the same shape is a data change.

## The doctor reports capability state

"Installed" was the only state it knew, and it is the least informative one. Six
now: what `install-state.json` actually recorded, registered and where, keyless
tools, credentialled, schema cost, and why something is deliberately not
registered.

The first cut of that got the headline wrong in its own field name: `installed`
was computed as `registered OR credentialled` -- the exact conflation this
release is named after -- and shipped into `installed-state-doctor.json` where a
machine reader would have believed it. It reads the recorded install status now,
or says `unknown`.

It immediately earned its place — on the development machine:

```
firecrawl-mcp  registered: Claude,Codex,Grok,Kimi   2 keyless, no key, 9080 tok/turn
```

Four providers paying ~9,080 tokens a turn each for two tools they already have.

Its first cut was wrong twice, both worth recording because both produced a
confident false negative rather than an error:

- It called `Test-V5ServerDeclared -Provider ...`; that function takes a
  resolved config target, so every call threw into a `catch` and the column read
  **"registered: none"** on a machine where everything was registered.
- Catalog ids are not always the registered server name — `codebase-memory`
  registers as `codebase-memory-mcp`, `github-mcp-server` as `github`. Now
  declared as `server_id` in the catalog rather than guessed by appending
  `-mcp`.

The column is also labelled machine-wide, because capability profiles are
project-scoped by design and would otherwise read as absent.

## Codex: the brief's remedy does not work

The plan said to shorten skill descriptions to fit Codex's budget. Measured with
`codex debug prompt-input` against throwaway `CODEX_HOME`s:

| case | skills | written | rendered | per description |
|---|---|---|---|---|
| baseline | 146 | 24,687 | 12,659 | ~88 chars |
| every description cut to 60 | 146 | 8,760 | 10,098 | ~71 chars |
| 60 skills, full descriptions | 60 | 10,240 | 11,508 | ~183 chars |

Cutting 65% of the written characters gave **no entry more room** — the rendered
total simply got smaller. The allowance follows entry **count**. At the bundle's
146 skills, 142 descriptions are already being truncated to about 88 characters.

**So nothing was trimmed.** Rewriting 146 descriptions across five provider trees
would have been a large, risky edit that measurement says buys nothing.

What does move it is entry count, and the biggest item is not the bundle's:

```
~/.codex/skills on the development machine   217 entries
  140  canonical bundle skills
   70  the OPTIONAL Other-Games mega-pack -- a MANUAL extra the installer never deploys
    7  stale duplicates and toolkit leftovers
```

The doctor now says that, with the numbers and the reproduction command, instead
of quoting a token figure and a remedy that does not work.

**Still unsolved, and stated as such:** at 146 skills this pack alone exceeds the
roughly 100 entries where Codex keeps descriptions intact. Truncation preserves
the prefix, and the prefixes still carry signal (no description leads with less
than 25 characters of real content, and only four collide in their first 40), so
routing degrades rather than dies. A provider-aware subset deployment is the real
fix and is too large for a corrective release.

## Also fixed

**v7.9.8.5 broke its own doctor.** It was the pack's first four-part version and
widened `check_versions.py` and `test_release_contract.py::test_version_sources`
accordingly — but not `TOOLS/Test-Installed-State.ps1`, which still required
exactly three parts. The installed-state doctor therefore failed the release that
shipped it, on a correct tree:

```
XX  Pack VERSION.txt is not a semantic version: v7.9.8.5
```

Widened, and a contract now asserts that **every** version gate accepts the
shipped version, so a format can never again be agreed by two checks out of
three.
