# v8.6.12 -- the offline archive was shipping last month's tools

**2026-08-27.** Based on v8.6.11. **164 canonical skills**, unchanged. A
full-bundle currency audit: three of seven offline payloads were stale, seven
pinned versions were behind, and a hook was found telling every agent to use
tools that were not registered.

---

## The Full-Offline archive shipped versions the pack no longer pins

`BUNDLED-TOOLS/offline/` carries the payloads that make a network-free install
possible. It is the one directory nothing regenerates on its own, and it had
drifted:

| Payload | Shipped | Latest | |
|---|---|---|---|
| `headroom_ai` | **0.35.0** | 0.36.5 | stale |
| `github-mcp-server` | **1.10.1** | 1.11.0 | stale |
| `codebase-memory-mcp` | Aug 20 build | 0.10.8 | stale |
| `houseCARL` | 1.9.0 | 1.9.0 | current |
| `spookys-automod-toolkit` | v1.11.2 | v1.11.2 | current |
| `superpowers` | v6.3.0 | v6.3.0 | current |
| `ponytail` | v4.9.0 | v4.9.0 | current |

Found by running the installer rather than reading it. `-Mode BundledFirst`
reported `pip install ...\offline\headroom_ai-0.35.0-...whl` immediately after
`Update-From-GitHub.ps1` had downloaded **0.36.5** — because that updater writes
to `BUNDLED-TOOLS/cache/` and the installer reads `BUNDLED-TOOLS/offline/`.
Two directories, one of them refreshed, and only `-UpdateCatalogOffline` bridges
them. Anyone installing Full-Offline got headroom 0.35.0 and
github-mcp-server 1.10.1 no matter how current the catalog said they were.

All three refreshed, the superseded files removed, `OFFLINE-MANIFEST.json`
regenerated from the actual bytes on disk, and the two version-stamped
`offline_asset` names in `CATALOG.json` updated to match.

## A hook was steering every agent at tools that were not there

`codebase-memory-mcp` installs its own `SessionStart` hook. On the maintainer's
machine it was emitting **695 bytes** of

> CRITICAL - Code Discovery Protocol: 1. ALWAYS use codebase-memory-mcp tools
> FIRST for ANY code exploration...

naming six tools, on every startup, resume, clear **and** compact — while
`codebase-memory` was registered on no provider at all. This pack profile-gates
most of its MCP servers deliberately, so "a hook instructs" and "the server is
registered" drift apart silently, and the cost is invisible: the instructions
reach the model, the tools do not.

The doctor now reports it. Two properties keep the check honest:

- **A hook that emits nothing is not flagged.** cbm's *other* hook shells out to
  a binary and exits; its own comment says it "NEVER blocks a tool call".
- **A hook that gates itself is not flagged**, checked across the whole body.
  A gate is invoked by piping the payload into it
  (`printf ... | gate || exit 0`), and that `printf` is the hook *asking*, not
  the hook speaking. A first draft anchored on the first print construct, read
  the guard as arriving too late, and flagged a hook that was already correct.

Reported, never rewritten — the same rule the autostart check follows. These
hooks belong to the tools that installed them.

## Correction: the cbm gate does not force anything

`docs/TOOL-EVALUATIONS.md` said, while rejecting lean-ctx, that the
`cbm-code-discovery-gate` hook "already forces agents to reach for" cbm first,
and called the capability "mandatory". Reading the hook shows it does neither:
its own comment says it never blocks a call, it only adds context, and it exits
0 silently when the binary is missing. The hook that *instructs* is
`cbm-session-reminder`, and that one was firing unconditionally. The rejection
of lean-ctx still stands on its own measurements; the reasoning around it was
overstated.

## A marketplace outlived its tool, and spread

`claude-mem` was uninstalled weeks ago and 1.29 GB of its payload had already
been reclaimed. Its **registration** survived all of it:

- still in Claude's `known_marketplaces.json` **and** `settings.json`
- still cloned at 140 MB under `plugins/marketplaces/thedotmack`
- plus **four orphaned 140 MB temp clones** from interrupted syncs, registered
  nowhere at all
- and synced into `~/.grok/marketplace-cache`, where grok reported
  `thedotmack (0 plugins) [error] Git sync failed: failed to lock cache`

The user never registered anything in Grok. **Grok inherits Claude's
marketplace list**, so one dead entry upstream became a failing entry
downstream. Registration is additive in every provider --
`Install-Provider-Starter-Settings.ps1` only ever *adds* to
`extraKnownMarketplaces`, and nothing anywhere removes an entry when the tool
behind it goes away.

`RETIRED-SKILLS.json` had solved exactly this for skills since 8.2.0. New
**`BUNDLED-TOOLS/RETIRED-PLUGINS.json`** does it for marketplaces, and
`Clean-StaleState.ps1` -- which the installer already runs with `-Apply` at the
end of every install -- now clears them across all three registration shapes:
Claude's JSON registry and settings, Codex's `[marketplaces.*]` and
`[plugins."*@*"]` tables, and Grok's cache, whose directories are **hashed** and
so can only be identified by reading each one's git remote.

Three rails, because a deletion list that can remove a live entry is worse than
no list:

1. **Name *and* URL must match**, so a marketplace re-pointed at a fork is safe.
2. **Never touch one whose plugin is still installed or enabled.** This is not
   hypothetical: `claude-mem` is still shipped, opt-in behind `-WithClaudeMem`,
   and its catalog entry registers this very marketplace. Without the
   `installed_plugins.json` check the install-time cleanup would unregister
   what that same install had just registered, **on every run**. Verified by
   simulating a fresh `-WithClaudeMem` state: the cleaner reports and skips.
3. **Every edited config is backed up first.**

Applied here: 286 MB freed, two registrations dropped. Grok then re-synced on
its own and came back with six marketplaces, all legitimate -- claude-mem did
not return, which is the inheritance chain confirming the fix from the other
end.

One caveat the tool now prints itself: **a running session holds its config in
memory and writes it back on exit.** The first removal in this session was
undone that way, by one of fourteen live `claude.exe` processes, about ninety
minutes later. Close the apps before trusting it.

## Editing a canonical skill shipped nothing, and the gate said green

Caught while fixing the section above, on this repo, in the middle of this
release.

`_CANONICAL-SKILLS` is the authoring tree. `INSTALL-AIO` copies from
`1-TAILORED-PROVIDER-TREES/<Provider>/COPY-TO-SKILLS-DIRECTORY/skills`, which
`TOOLS/fanout_providers.py` generates. Skip the fanout and the edit exists only
where nothing reads it.

So: two skills corrected, **104 contracts green**, pack gate PASS, installer
reporting `Claude skills installed` ... `Hermes skills installed` -- and every
provider copy still yesterday's file, timestamped `2026-08-26 21:06`. Nothing
failed. Nothing shipped. The only reason it surfaced is that the change was
checked on disk afterwards instead of being assumed.

Two existing contracts touch this and neither could catch it:

- one byte-compares canonical against the trees for a short list of "v7.8
  reliability skills";
- the other compares only the **set of skill names** per tree, never contents.

Both edited skills were outside the first list, so only the name check applied,
and the names had not changed.

The new contract compares **all 164 skills across all five trees**, normalising
exactly two things and no more:

- the nested `provider:` metadata line, which the fanout rewrites per target and
  is the only intended per-provider tailoring;
- line endings, because `unrestraint-packs` carries mixed EOLs in canonical
  that the fanout emits as CRLF -- cosmetic, predates this check, and failing on
  it would just train people to ignore the contract.

Its failure message names the command:
`python TOOLS/fanout_providers.py _CANONICAL-SKILLS .`

Falsified by reverting one provider copy to yesterday's content.

Same shape as the context7 pin earlier in this release: a value in two places,
and the second copy is the one that ships. That pattern has now cost this
release two separate defects, which is enough to call it the pack's most
expensive recurring failure.

## "It never told me to change profile. I don't even know how."

Reported from a real Grok transcript: the agent tried houseCARL and Skyrim
Forge tools, both searches returned nothing, and it concluded *"houseCARL and
Forge MCP are disconnected"*. Both tools were installed. Both were one command
from working. Nothing in the pack said so.

Gating MCP servers on cost is defensible -- houseCARL alone is ~41,768 tokens
*every turn*. Failing with no path forward is not, and calling that "working as
designed" would be hiding behind the design. Three holes, all of them ours:

**1. The router told users to install what they already had.**
`skyrim-tool-router` said *"if a tool is missing, load `tool-discovery` and
recommend install"*. houseCARL **is** installed; following that advice sends
someone to reinstall a working tool. It now separates the two failures, because
they need opposite answers:

| Symptom | Meaning | Answer |
|---|---|---|
| MCP tool search returns 0 results | installed, **not enabled for this project** | give the enable command |
| binary absent from disk | not installed | recommend install |

**2. `tool-discovery` had only one failure mode.** `TOOL MISSING` was the whole
vocabulary. It now has a `TOOL PRESENT BUT NOT ENABLED HERE` template carrying
the exact commands, the profile names worth knowing (`game-skyrim-load-order`
for houseCARL, `game-skyrim` for Forge, `code-intel`, `web`), and the part
everyone forgets -- **restart the app**, because a running session does not pick
up a newly registered MCP server.

**3. The installer never ran the detection it advertises.** `INSTALL-AIO` calls
`Set-McpProfile -Auto` **only when `-WorkspaceRoot` is passed**, and
`START-HERE.bat` never passes it. So on a default install that detection had
never run once, while the closing text cheerfully listed the command among
eight other bullets. It now reports the actual state:

```
NONE are enabled for any project yet. Until you enable one, houseCARL,
Skyrim Forge, codebase-memory and Serena tools will NOT appear in any AI
app, and an agent asked to use them will simply find nothing. That is a
one-command fix, not an install problem:
  TOOLS\Set-McpProfile.ps1 -Detect -Path "<your project>"   # what applies
  TOOLS\Set-McpProfile.ps1 -Auto   -Path "<your project>"   # enable it
```

and when profiles *are* enabled it lists them instead. Read from
`mcp-profiles.json`, so it reflects reality rather than reciting a sentence.

It still refuses to guess a project directory and enable servers for it --
wiring the wrong project would be worse than saying nothing. But saying nothing
is what it used to do.

For the record: `Set-McpProfile` has supported Grok since it existed. The
command is identical on Claude, Codex, Grok, Kimi and Hermes.

## Running the installer with your AI apps open failed the whole install

The worst thing found today, and it was found by checking whether this
release's own version bump had actually landed. It had not:
`github-mcp-server` was still 1.10.1 on disk while the catalog and the offline
payload both said 1.11.0. Re-running the installer explained why:

```
==> Component: GitHub MCP Server (official) [github-mcp-server]

=====================================================
 INSTALL FAILED
 robocopy failed exit=8 from=...uabs-extract-github-mcp-server-248240849
```

Four `github-mcp-server` processes were alive as MCP servers for open Claude,
Codex, Grok, Kimi and Hermes sessions. Their binary cannot be overwritten,
robocopy answers that with **exit code 8**, `Copy-UabsRobo` turns exit >= 8
into a throw, and the throw aborts **everything**. One locked file and the
entire run stops.

That is not an edge case. It is what happens when a user double-clicks
`START-HERE.bat` without closing their AI apps first -- the normal way anyone
would run it.

houseCARL and codebase-memory already handled this, with
`Test-UabsFileLocked`, `Stop-UabsProcessUsingExecutable` and
`Copy-UabsRoboSafe`. The **generic `zip-extract` branch** that every other
component falls through to had none of it, and `github-mcp-server` falls
through to it. The machinery existed; one branch never got wired to it.

Now it does, with one deliberate difference. codebase-memory *throws* when a
file will not release; the generic branch **skips that one component with a
warning** instead:

```
!!  github-mcp-server: binary in use, left at the installed version -- github-mcp-server.exe
    Close every AI app (their MCP servers hold this file) and re-run to update it.
    Nothing else in this install was affected.
```

Aborting an entire install over one MCP binary is disproportionate, and a user
cannot act on `robocopy failed exit=8` without being told which file, why, and
what to do.

Re-running the same command that had just failed: exit 0, no `INSTALL FAILED`,
processes stopped, and **github-mcp-server 1.10.1 -> 1.11.0**. The skip path is
the fallback; the normal outcome is that the update simply works.

## An unread version string is still a claim

`BUNDLED-TOOLS/PROFILES.json` declared `pack_version: 8.0.0` and
`catalog_version: 8.0.0` while the pack shipped through 8.6.x. Nothing reads
those fields -- which is exactly why they rotted, and exactly the wrong reason
to leave them. It is a file users open to understand why most MCP servers are
off by default, and it was telling them it described a pack six minor versions
old.

Corrected, and added to `check_versions.py` so CI fails on the next drift
rather than waiting for someone to notice. Falsified by reverting it to 8.0.0.

## Twelve files were shipping unverified

`verify_manifest.py` proves every **recorded** file exists. Nothing proved
every **existing** file is recorded, and that asymmetry hid two bugs for as
long as the manifest has existed:

1. `git ls-files` **octal-quotes** any path containing a non-ASCII byte. An em
   dash came back as `"0-UNRESTRAINT-PACKS/AIO-INSTRUCTION \342\200\224
   Compact.md"`, quotes included, while `os.walk` yielded the real name. They
   never matched, so **eleven** tracked files were dropped from the manifest in
   silence. Fixed with `ls-files -z`.
2. `MANIFEST.json` was skipped by bare *name* anywhere in the tree, which also
   excluded the vendored Forge manifest at
   `BUNDLED-TOOLS/skyrim-forge/MANIFEST.json`. Now skipped only at the root,
   where it genuinely cannot hash its own output.

`MANIFEST.json` went from **5,428** entries to **5,440** -- exactly the tracked
file count, zero uncovered, zero phantom. Both failures are invisible to a
verifier that only walks the manifest, which is why the new contract walks the
other direction.

Its first version then died with a `UnicodeEncodeError` while *reporting* the
problem, because the offending names are non-ASCII by definition and the
console is cp1252. Escaped now: a contract that cannot print its own failure is
not a contract.

One process note, since it caused this: **regenerate the manifest after staging,
not before.** The commit before this one recorded 5,425 files while three more
were staged moments later, and every gate passed anyway.

## The catalog was decorative for the server every provider runs

Bumping `context7` 4.0.2 -> 4.0.3 should have been the easy half of this
release. It was measured, its capability record regenerated, the catalog
updated, contracts green, CI green. Then a full installer re-run left **all
five providers still pinned to 4.0.2** -- Claude, Codex, Grok, Kimi and Hermes,
every one of them.

`TOOLS/Add-Reasoning-MCPs.ps1`, which wires the always-on core onto every
provider, carried its own hardcoded `@upstash/context7-mcp@4.0.2`. The catalog
was never consulted. So the pin in `CATALOG.json` -- the file this pack treats
as its statement of truth, the one whose version a contract binds to the
measured capability record -- had no effect on any machine.

The file's own comment already said CATALOG entries "carry a version to check
rather than only a pin to trust". The duplicate sat four lines below it.

Now resolved from `CATALOG.json`, with the literal kept only as a fallback for
an unreadable catalog, so damage degrades to "one release behind" rather than
"unpinned". Re-wired with `-Refresh`; all five providers verified at **4.0.3**.

A contract pins both halves and was falsified both ways: restoring the
hardcoded pin in the server entry fails, and so does letting the fallback drift
*newer* than the catalog -- a fallback ahead of the catalog would install a
version nothing measured, on exactly the machines whose catalog is broken.

**This one is worth generalising.** Every number this pack ships is only as
good as the last place that reads it. A version living in two files is a
version in the wrong place, and the second copy is invisible precisely because
the first one is correct.

  directories, on all five providers. Red skill names in a Grok transcript are
  its theme, not errors.
