# v8.6.7 -- the skill Codex already had

**2026-08-27.** Based on v8.6.6. **164 canonical skills**, unchanged. One defect
v8.6.6 introduced, caught by this pack's own doctor on the first real install,
and fixed for its whole class rather than for the one case.

---

## The collision

v8.6.6 adopted `skill-creator` into `_CANONICAL-SKILLS/` on the reasoning that a
canonical skill reaches all five providers where a plugin reaches one. That
reasoning was right for Claude, Grok, Kimi and Hermes.

It was wrong for Codex, which ships a `skill-creator` of its own. Codex carries
built-in skills in `<CodexHome>\skills\.system`, and the live index showed both:

```
r0 = C:/Users/karlo/.agents/skills          <- this pack
r1 = C:/Users/karlo/.codex/skills/.system   <- Codex's own

- skill-creator: Guide for creating effective skills...   (file: r1/skill-creator/SKILL.md)
- skill-creator: Create new skills, modify and improve...  (file: r0/skill-creator/SKILL.md)
```

The final doctor said so plainly on the first install after the release:
`Codex indexes 1 skill(s) twice`.

That warning is not cosmetic. Codex splits a fixed index budget across every
entry, so one surplus entry narrows **every** description:

| | entries | visible description chars |
|---|---|---|
| with the duplicate | 184 | 48 |
| without it | **183** | **50** |

## Fixed by discovery, not by name

Hardcoding `skill-creator` would have fixed this collision and left five more
loaded. `.system` also holds `imagegen`, `openai-docs`, `plugin-creator`,
`review-agent` and `skill-installer`; any future canonical skill taking one of
those names collides identically, and a name list would not catch it.

`Get-UabsCodexBuiltinSkillNames` reads the `.system` root and treats a directory
as an owner only when it actually carries a `SKILL.md` -- an empty or
half-written folder owns nothing, and treating it as an owner would evict the
pack's working copy in favour of nothing.

## It reuses the remover that already refuses to lose work

The removal goes through `Remove-UabsPluginOwnedSkillCopies`, the same function
the native-plugin dedupe uses:

- md5 of the copy's `SKILL.md` against canonical, and a **mismatch is refused**,
  not deleted -- a difference means the user may have edited it;
- robocopy backup to `backups\dedupe-Codex-<timestamp>\<name>` before any
  `Remove-Item`;
- a copy with no `SKILL.md`, or a name absent from canonical, is kept and the
  reason recorded.

Only the *owner* differs: an enabled plugin there, Codex itself here. Nothing
about the safety changes, because none of it should.

## The doctor accounts the two separately

```
Codex bundled skills accounted: 143 exact file(s), 20 native-plugin-owned,
1 owned by Codex itself, 164 expected.
```

Separately on purpose. "A plugin ships this" and "Codex ships this" are
different facts with different remedies, and a reader who cannot tell them apart
cannot act on either. Without the accounting at all it is worse than cosmetic: a
skill the installer correctly removed reads as a **missing** skill and fails the
run, so the fix would have traded a warning for an error.

The duplicate warning also stopped calling a built-in "an enabled plugin", which
is what it had said while pointing at one.

`skill-creator` still installs to Claude, Grok, Kimi and Hermes. Only Codex,
which already has one, goes without.

## Contract

94 contracts, green. The new one asserts the discovery exists, reads `.system`,
requires a `SKILL.md`, contains no hardcoded skill name, is called by the
installer, routes through the verified remover, and is understood by the doctor.

It was falsified four ways and catches all four: a hardcoded name list, the
installer dropping the call, the doctor blind to built-in ownership, and the
verified remover bypassed for a direct delete.

One of those four took two attempts. The first mutation replaced the *first*
`Remove-UabsPluginOwnedSkillCopies` in the installer, which lives in the plugin
wrapper rather than in the new block, so the contract passed and was briefly
mistaken for a gap. A falsification that does not mutate the code the contract
actually reads proves nothing about either.
