# v8.6.5 -- The setting nobody looks at

**2026-08-26.** Based on v8.6.4. 160 canonical skills, unchanged. The LM Studio
folder gains the settings, not just the arithmetic.

---

## v8.6.4 got the cause right and the fix wrong

That release documented KV-cache spill as the reason a local model is quick in a
fresh chat and unusable later, and told you to enable cache quantisation.

On the machine it was measured against, cache quantisation was **already on**,
at `q8_0`. The real configuration was:

```
llm.load.contextLength                 64000
llm.load.llama.kCacheQuantizationType  q8_0
llm.load.llama.vCacheQuantizationType  q8_0
llm.load.numParallelSessions           2
```

`numParallelSessions` is a **multiplier on the entire cache** -- every parallel
session gets its own. Nothing in the name suggests it costs VRAM, so nobody
looks at it, and it was quietly doubling a cache that already did not fit.

Measured: 16 GB card, 10.26 GB weights, 4.23 GB left after a 1.5 GB desktop
reserve, at 65,536 context.

| sessions | K/V quant | cache wanted | verdict |
|---|---|---|---|
| **2** | q8_0 | 16.3 GB | what it was actually set to |
| 2 | q4_0 | 8.1 GB | still over |
| 1 | fp16 | 16.3 GB | over |
| 1 | q8_0 | 8.1 GB | over |
| **1** | **q4_0** | **4.1 GB** | **fits** -- max context 68,205 |

So on this card the model reaches the 64,000 Hermes demands in exactly one
configuration: one session, q4_0 K and V. Quantising alone was not enough, and
neither was dropping to one session alone. "Enable KV quantisation" was true and
insufficient.

## Get-KvBudget.ps1

Reads the GGUF header and the GPU, prints the maximum context at fp16, q8_0 and
q4_0, and takes `-Sessions` so the multiplier is visible instead of implied.
Read-only.

It also names the field that catches people out: `key_length`. The common value
is 128; this model ships **256**, which doubles its cache against a same-size
model, and no model card mentions it.

```
layers 65  kv_heads 4  key_len 256  value_len 256
  key_length 256 is double the common 128 -- this model costs twice the cache
KV per token     : 266,240 bytes at fp16  (0.254 MB)
```

Where `key_length` is absent the script falls back to
`embedding_length / head_count` and says so, rather than printing a number whose
origin is invisible.

## A preset that carries load settings, not just sampling

The three presets shipped in v8.6.4 all had an empty `"load": {"fields": []}` --
sampling only. `Hermes 16GB` fills it:

| key | value |
|---|---|
| `llm.load.contextLength` | 65536 |
| `llm.load.llama.flashAttention` | true |
| `llm.load.llama.kCacheQuantizationType` | q4_0 |
| `llm.load.llama.vCacheQuantizationType` | q4_0 |
| `llm.load.llama.acceleration.offloadRatio` | 1 |
| `llm.load.numParallelSessions` | 1 |

Every key and value shape was read out of LM Studio's own
`user-concrete-model-default-config` files. None were guessed, which matters
here: an invented config key does not error, it is silently ignored, and the
setting you believed you applied was never applied.

It is named for the card it was computed against. On 24 GB, q8_0 is affordable
and keeps more cache fidelity -- run `Get-KvBudget.ps1` rather than assuming
this preset is right for you.
