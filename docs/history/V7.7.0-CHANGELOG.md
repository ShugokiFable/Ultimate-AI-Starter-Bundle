# v7.7.0 — the harness has to actually load it

Three of the five providers were carrying the whole bundle on disk while their
harness never loaded any of it. Every prior gate said PASS, because every prior
gate asked "is the file there".

## Kimi has a native plugin system, and the installer said it did not

The symptom the operator reported was "Kimi has the brain but doesn't use my
addons properly". The installer's own comment explained why it would not:

```text
Kimi    no plugin command in kimi-code CLI 0.27.0 - copied skills only.
```

The observation is correct. There is no `kimi plugin` subcommand — the shipped
CLI's command list is export, provider, acp, server, web, login, doctor, vis,
migrate, upgrade. The conclusion drawn from it is not. Kimi's plugin system is
driven by an in-session `/plugins` slash command, and the shipped binary is
full of it: `/plugins` ×27, `plugins install` ×3, `sessionStart` ×47,
`plugin.json` ×8.

Worse, **the bundle already contained the correct Kimi adapter**:
`BUNDLED-TOOLS/plugins/superpowers/.kimi-plugin/plugin.json`, declaring

```json
"skills": "./skills/",
"sessionStart": { "skill": "using-superpowers" }
```

plus a full Kimi tool mapping (`AskUserQuestion`, `TodoList`, `Agent` with
`coder`/`explore`/`plan` subagents). `sessionStart.skill` is exactly the hook
that makes Superpowers bootstrap itself every session instead of sitting inert
as files. It was shipped and never wired.

### Why the registry is written directly, and why that is safe

`kimi -p "/plugins install <path>"` is not an option: prompt mode demands a
login before it will run anything, and an installer cannot assume the operator
is authenticated. So the install path is reproduced directly. Reading the
shipped CLI gives the exact contract:

- `copyPluginToManagedRoot(kimiHomeDir, id, sourceRoot)` →
  `<home>/plugins/managed/<id>`, staged into a temp dir then renamed
- the registry is `<home>/plugins/installed.json`, `{version: 1, plugins: []}`
- `persist()` writes a **thin** entry: `id, root, source, enabled,
  installedAt, updatedAt, originalSource, capabilities, github`
- on load, `materialize(entry)` calls `parseManifest(entry.root)` and rebuilds
  `manifest`, `skillCount` and `state` **from disk**

That last point is what makes this safe rather than brittle. Nothing here
reimplements Kimi's manifest parsing, and a Kimi upgrade that changes the
manifest schema cannot leave a stale record behind — the record does not carry
one. The manifest is read from `<root>/plugin.json` or
`<root>/.kimi-plugin/plugin.json`, which is where the bundled adapter lives.

Existing entries are preserved field-for-field, including nested objects like
`github`, and a corrupt `installed.json` is backed up rather than overwritten
in place.

## Hermes lost its bootstrap to every compaction

The adapter registered `pre_llm_call` and returned the bootstrap when
`is_first_turn` was set, `None` otherwise. Hermes injects that context into the
first turn's user message — which is precisely the part a compaction
summarises away. So: long session, compaction, bootstrap gone, and the plugin
never puts it back. Superpowers silently stopped applying partway through
exactly the long runs that need it most.

`BOOTSTRAP_MARKER` already existed in the file and was only ever used as
display text. It is now the test: inject on the first turn, stay quiet while
the marker is still somewhere in `conversation_history`, and inject again once
it is gone. When the host does not supply a history at all, first-turn
behaviour is kept rather than injecting on every request.

`TESTS/test_hermes_bootstrap.py` covers all of it — first turn, marker
present, marker gone, history absent, and two malformed history shapes that
must not crash the hook. It was confirmed to fail against the old adapter
(`AssertionError: must re-inject after compaction`) before being trusted.

## The plugin scanner was being switched off permanently

Both bundled plugins trip Hermes' install-time security scanner with
false-positive traversal findings, and `--force` does not override it. The
previous fix wrote `plugins.scan_on_install: false` into the operator's
`config.yaml` and then deliberately **re-asserted it after** the install and
restart window, so it would survive.

That is not a scanner disabled for our install; that is a scanner disabled for
every third-party plugin the operator ever installs afterwards. Hermes treats
plugin loading as an explicit trust boundary and that call belongs to the
operator.

The override is now removed once the bundled plugins are in, and the shipped
`config.yaml` no longer carries it at all. The restore removes a single line
rather than restoring a snapshot, because the Hermes gateway re-serialises
`config.yaml` on its own schedule and a snapshot would clobber whatever it
legitimately wrote in between. An operator who had their own
`scan_on_install` setting keeps it untouched.

## Claude: install, not just detect

The Claude branch only ever detected an existing native install. It now uses
Claude's own plugin CLI when it is on PATH, and takes the marketplace name from
each plugin's own `.claude-plugin/marketplace.json` rather than guessing —
Superpowers publishes as `superpowers-dev`, Ponytail as `ponytail`, and those
names are what Claude uses for both the install target and the cache directory
it verifies against. Success is confirmed by the cache directory appearing, not
by an exit code.

It deliberately does **not** hand-write `plugins/cache/<marketplace>/<plugin>`
and its `.install-manifests` entry. That manifest is a per-file SHA256
integrity map; forging one means reimplementing Claude Code's own verification
against a format that cannot be tested from here. Kimi's registry was safe to
write because the CLI re-derives every record from disk. This one is not, and
Claude is the provider that currently works. Without the CLI the copied skills
remain, which is a working fallback, and the exact two commands are printed.

A separate bug: the bundled `TOOLS/hooks/plugin/.claude-plugin/marketplace.json`
had gained a `superpowers` entry pointing at `./superpowers`, a directory that
does not exist. A marketplace with a dangling source does not merely fail to
install that plugin — it invalidates the marketplace for the working
`completeness-gate` plugin too. Removed.

## What was checked and left alone

The plugin-owned skill dedupe was reported as broken, on the reasoning that it
compares the upstream plugin's `SKILL.md` against the canonical copy and so
would leave differing skills duplicated.

It does not do that. Ownership comes from `Get-V5PluginOwnedSkillNames`, which
reads the plugin's own `skills/` directory at install time — the
install-time exclusion behaviour that was being asked for. The MD5 comparison
is between the **installed provider copy** and the pack canonical, answering a
different question: "is this copy still the unmodified thing we put there, or
has the operator edited it?" A difference means *keep it and warn*, which is
the correct behaviour and the reason nothing was silently deleted.

Measured against the real trees: all 20 plugin-owned skills shipped as copies
are byte-identical to canonical, so the dedupe removes 20 of 20 and leaves
zero duplicates. On the live machine it removed 14 for Kimi, refused none, and
backed up every one. The logic was left as-is; replacing it with blind
exclusion would delete operator-modified skills without warning.

One real improvement did come out of it: the new harness test only counts a
copied skill as a duplicate when the native plugin for it is actually
installed. Grok has no native Ponytail, so its six Ponytail copies are the
delivery path, not duplicates — the first version of the test flagged them and
would have argued for deleting the only working copy.

## Release builder

`TOOLS/Build-Release.ps1` produces two artifacts from `git archive HEAD`:

| | contents |
|---|---|
| `...-Core.zip` | everything except `BUNDLED-TOOLS/offline/` |
| `...-Full-Offline.zip` | adds the 135 MB of vendored installers |

Staging from `git archive` rather than copying the working folder excludes
`.git` (~200 MB) and the gitignored `BUNDLED-TOOLS/cache/` (~133 MB) *by
construction*, along with `__pycache__`, `.venv`, `.env` and anything
uncommitted. A zip of the working folder carries all of it — that is the
difference between a 470 MB folder zip and these artifacts.

The forbidden-path check still runs and **fails** the build rather than
deleting quietly: if one of those paths ever reaches staging, what git tracks
has changed and that deserves a look. The builder also refuses to run against
a dirty tree, since `git archive HEAD` would ship the last commit while the
operator is looking at uncommitted work.

## Harness realization tests

`TESTS/Test-HarnessRealization.ps1` reports per provider whether the harness
would actually load the bundle: native plugin registered where that provider's
loader reads it, Kimi's `sessionStart` declared, Hermes' adapter re-injecting,
the preamble present and provider-neutral and free of `U+FFFD`, no duplicate
plugin-owned copies, and the scanner restored.

Run against this machine before the fixes: **7 failures**. After: **16 pass, 0
fail, 2 skip**. Codex and Grok report SKIP rather than PASS — a staged plugin
directory is not proof that either harness loaded it, and inventing a verdict
is the exact failure mode this script exists to catch.
