# v7.6.4 — Grok hooks need the PowerShell call operator

Found by user report: after installing the bundle, Grok printed two hook
errors on every single tool use:

```text
global/ultimate-bundle:pre_tool_use[0].hooks[0]
   failed with exit code 1: At line:1 char:65
```

## Root cause

`At line:1 char:65` is a PowerShell *parse* error, not a gate verdict. Grok
executes hook commands through PowerShell. The completeness-gate installer
wrote the same command string for every provider:

```text
"C:\...\python.exe" "C:\...\gate.py" --pre
```

That is valid cmd.exe (Claude Code's shell) and invalid PowerShell: a quoted
string followed by more tokens is not an invocation without the call operator.
Char 65 is exactly where the second quoted string begins. The gate scripts
never ran; PowerShell rejected the line before anything executed, twice per
tool call (two gates wired into `PreToolUse`).

The wiring was tested on Claude and Codex, whose shells accept the cmd form.
Grok's shell was never exercised, so the failure mode shipped.

## Fix

`New-HookBlock` in `TOOLS/Install-Completeness-Gate.ps1` gained a
`-CallOperator` switch that prefixes each command with `& `:

```text
& "C:\...\python.exe" "C:\...\gate.py" --pre
```

Only the Grok branch sets it. The prefix is not applied globally because
cmd.exe chokes on a leading `&` — what fixes one shell breaks the other, so
each provider gets the syntax its own shell parses. Codex's plugin
`hooks.json` uses bare `python "..."`, which both shells accept, and is
untouched.

The live `~/.grok/hooks/ultimate-bundle.json` was rewritten by re-running
`Install-Completeness-Gate.ps1 -Providers Grok`, then repointed at the stable
WindowsApps python launcher instead of the daimon managed venv the resolver
had selected — that venv belongs to another agent's runtime and can disappear
out from under the hooks.

## Verification

Reproduced first: the exact command line from the broken hook file, run
through PowerShell, fails with `At line:1 char:65` at the second quoted
string. After the fix, all four wired commands (2 gates × `--pre`/`--stop`)
were executed in the exact `& "py" "script" --flag` form Grok receives, with
`'{}'` piped as stdin: all parse, all exit 0.

## Not changed

- Claude's hook block — the unprefixed form is the only one cmd.exe accepts.
- Codex's plugin hooks — already shell-neutral.
- Gate logic itself — the scripts were never the problem; they never ran.
