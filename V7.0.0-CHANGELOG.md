# V7.0.0 — codebase-memory indexing discipline

**Date:** 2026-08-15
**Base:** v6.9.3
**Runtime status:** tool-validated. Every claim below was measured on a real
45-project index on the author's machine, not inferred from documentation.

## Why this is a major bump

Through v6.9.3 the pack documented how to **query** the knowledge graph and said
nothing about how to **build** one. That gap has a direct cost: an agent told to
"index the repo" points `index_repository` at a Skyrim mod root and produces a graph
of vendored headers, duplicated version snapshots and animation files. It then bills
tokens on every subsequent query and answers structural questions no better than grep.

This release adds the missing half. It is a major bump because it changes the
recommended procedure — `.cbmignore` before first index — rather than adding content.

## Evidence

A real index was rebuilt from scratch under these rules:

| | Before | After |
|---|---|---|
| Projects | 32 | 45 |
| Nodes | ~570,000 | **54,553** |
| Edges | — | 140,524 |

Worst individual offenders:

| Project | Before | After | What was actually in there |
|---------|--------|-------|----------------------------|
| For-Honor-In-Skyrim-BFCO | 235,567 | 577 | animation/mesh asset tree |
| NemesisCombatAI | 111,405 | 545 | 9 stale snapshots + vendored `extern/` |
| Modern-NPC-Pathing | 92,669 | 789 | 3,471 of 3,964 headers were CommonLibSSE in `extern/` |
| houseCARL | 24,507 | 9,006 | a 6.43 MB bundled `corpus.json` |
| Mantella-Woo-Sensorium | 13,301 | 7,509 | capitalized `Meshes` leaking past a lowercase rule |

## Findings encoded into the pack

### 1. `.cbmignore` matching is CASE-SENSITIVE

`meshes/` does not match `Meshes/`. Skyrim conventionally capitalizes `Meshes`,
`Textures`, `Sound`, `Interface`. A lowercase-only ignore list silently leaks whole
asset trees. `NemesisCombatAI` carried 18,067 nodes for 13 source files because of a
capitalized `Meshes` directory alone.

Every asset rule now ships in both cases, in the template and the generator.

### 2. Papyrus (`.psc`) is never indexed

There is no tree-sitter grammar for Papyrus, and the indexer additionally skips
directories named `scripts/` through a built-in skip-list — exactly where Skyrim keeps
`Scripts/Source/*.psc`.

Verified: a project with 309 `.psc` files reported its languages as PHP, YAML,
JavaScript, Python — no Papyrus. A `search_code` for `Event On` across a Papyrus-only
mod returned 0 results.

The skill now states plainly that Papyrus questions go to Grep + `papyrus-reference`,
and that a tiny graph for a script-only mod is the **correct** result. This matters
because the natural reaction to "5 nodes" is to loosen the ignore rules, which only
adds asset noise without ever recovering the Papyrus.

### 3. Versioned workspaces, and the source-carrier exception

A mod root holds many `Mod Name X.Y.Z/` snapshots; indexing all of them multiplies every
file by the snapshot count (`FaceForge` kept 34 copies, `NPC Spell Variance` 23).
Resolve the active version from `CURRENT.txt` and ignore the rest.

**But not blindly.** Where the active version is a packaged release, the source often
lives only in an older snapshot. Excluding "stale" versions there deletes the only copy
of the code from the graph. Measured cases:

| Project | Active | Source actually lives in |
|---------|--------|--------------------------|
| NemesisCombatAI | 1.0.8 (no C++ at all) | `1.0.0` — 13 files |
| Faster Loadin' 'n' Savin' | 1.5.1 (0 code files) | `-1.5.1-source` — 9 files |
| Mantella Woo Sensorium | 0.8.5 (2 files) | `0.7.0` — 45 files |
| For Honor In Skyrim BFCO | 2.0.6 (assets only) | `1.8` — 8 files |
| Build a follower | 2.5.9 (4 files) | `-2.5.0-SOURCE-READY` — 5 files |

`TOOLS/Setup-CodebaseMemory-Index.ps1` detects this by comparing code counts, and by
language family: an active version with tooling scripts but **zero** compiled-language
source is a package, not the source of truth.

Fallback rule when no `CURRENT.txt` exists: pick the **highest version**, never the
newest mtime — a touched old folder is not the active one.

### 4. Never-index list

Mod-manager staging (Vortex/MO2 `mods/`) was ~3,001 folders and 90,049 nodes on its own,
went stale on every mod change, and duplicated what `houseCARL` already answers from live
truth. Also excluded: tool install trees, agent session dumps, game `Data` as sole
authority, and bundled reference corpora served through skills.

### 5. Secrets and hostile filenames

- `.env` / `.env.*` are excluded everywhere. A graph is queryable; one project's `.env`
  held a live bot token.
- **A file literally named `nul` breaks the indexer.** `index_repository` fails with a
  bare "Pipeline failed" and writes no useful log. It is a reserved Windows device name,
  produced by a botched `... > nul` redirect. Verified by indexing a copy of the same
  project without it: succeeded at 159 nodes. If an index fails with "Pipeline failed",
  suspect `nul`/`con`/`aux`/`prn`/`com1` before suspecting the repo.

### 6. The dashboard lies about totals

On the Projects tab the **NODES and EDGES tiles read 0** even on a fully healthy index.
They bind to a selected project rather than aggregating, and nothing is selected there;
only the PROJECTS tile is a real total. This reads exactly like data loss and is not.

Confirmed against the tool's own endpoints: `/rpc list_projects` returned all 45 projects
with correct counts, and `/api/project-health?name=X` returned correct per-project
numbers, while the tiles showed 0. Note the parameter is **`?name=`** — `?project=`
returns HTTP 400.

The skill ships the PowerShell one-liner for a trustworthy total, and notes that in
PowerShell `curl` is an alias for `Invoke-WebRequest` and does not accept `-H`/`-d`.

### 7. There is no backup

Project graphs live under `%USERPROFILE%\.cache\codebase-memory-mcp\`. Deleting a project
from the dashboard is immediate and unrecoverable. What made a full rebuild cheap was a
written registry of what had been indexed and why. The skill now tells agents to keep one
and points at the `skyrim-memory` vault convention.

Installer and guide filenames (`INSTALL-V6-AIO.*`, `V6-AIO-GUIDE.md`) are **deliberately
unchanged**. They are referenced by three canonical skills, the `.bat` wrapper, and every
historical changelog; renaming them buys nothing and breaks links.

### Note for whoever runs `fanout_providers.py` next

`unrestraint-packs` lives in `_V6-CANONICAL-SKILLS` but is scoped to **Hermes only** by
v6.9.3's design. Because fanout treats canonical as the source of truth for *every*
provider, running it propagates that skill into all five provider trees as a side effect.
That was reverted in this release to preserve the Hermes-only scoping.

If you want it to stay Hermes-only, delete the generated
`{Claude,Codex,Grok,Kimi}/COPY-TO-SKILLS-DIRECTORY/skills/unrestraint-packs/` directories
after each fanout and regenerate `MANIFEST.json`. If you want it everywhere instead, keep
them and say so in that release's notes — but decide deliberately rather than inheriting
it from a fanout run.

Fanout also **rewrites line endings**. The two Hermes `unrestraint-packs/SKILL.md` files
were stored CRLF and came back LF with byte-identical content. `.gitattributes` sets
`* -text` precisely so a clone stays byte-identical and `MANIFEST.json` hashes verify, so
unintended EOL flips are real churn, not cosmetics. Both files were restored to their
committed bytes in this release. After any fanout, check
`git diff --cached --ignore-all-space` — anything that disappears under that flag is EOL
churn to revert, and remember to regenerate `MANIFEST.json` afterwards.
